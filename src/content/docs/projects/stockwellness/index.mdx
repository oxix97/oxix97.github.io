## 문제

시장 데이터는 수집 주기와 제공처가 다르고, 일부 날짜나 종목 데이터가 늦게
도착할 수 있습니다. 수집 성공 여부만 확인하면 누락된 데이터를 정상으로
오해하게 됩니다.

## 제약

- 외부 제공처의 응답 속도와 실패율을 통제할 수 없습니다.
- 배치 재실행은 중복 데이터를 만들지 않아야 합니다.
- 조회 API는 수집 작업과 독립적으로 응답해야 합니다.

## 검토한 선택지

하나의 애플리케이션에서 수집과 조회를 함께 처리하는 방식은 시작은 빠르지만,
배치 부하가 API 지연으로 전파됩니다. 수집·검증·조회 경계를 분리하면 초기
설정은 늘지만 실패 범위를 작게 유지할 수 있습니다.

## 선택과 구현

Spring Batch 작업이 원천 데이터를 적재하고 기준일·종목별 누락을 검증하도록
구성했습니다. API는 검증이 끝난 데이터만 조회하고, 재실행 가능한 upsert
규칙으로 중복을 방지합니다. PostgreSQL 인덱스는 실제 조회 조건을 기준으로
설계했습니다.

## 결과

수집 실패와 조회 장애를 분리해 원인을 좁히기 쉬워졌고, 특정 기준일을 다시
처리하는 절차가 명확해졌습니다. 다음 단계는 누락 감지 지표와 배치 실행
시간을 함께 모니터링하는 것입니다.
