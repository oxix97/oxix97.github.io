<summary>21. 생성자 주입을 권장하는 이유는 무엇인가요?</summary>


### 면접 답변

첫 번째로 필요한 의존성을 객체 생성 시점에 반드시 전달하도록 만들어 객체가 불완전한 상태로 생성되는 것을 막을 수 있습니다.

두 번째로 필드를 `final`로 선언할 수 있어 의존성이 실행 중 변경되지 않도록 만들 수 있습니다.

세 번째로 Spring 없이도 객체를 직접 생성해 테스트하기 쉽습니다.

또한 생성자 주입에서는 순환 참조가 애플리케이션 시작 단계에서 비교적 빠르게 드러납니다.

### 예상 꼬리질문

* Setter 주입이 적합한 경우는 언제인가요?
* Lombok의 `@RequiredArgsConstructor`를 사용하는 이유는 무엇인가요?

<summary>22. 생성자 주입, Setter 주입, 필드 주입의 차이는 무엇인가요?</summary>


### 면접 답변

생성자 주입은 객체 생성 시 의존성을 전달하기 때문에 필수 의존성을 표현하는 데 적합합니다.

Setter 주입은 객체 생성 이후 의존성을 설정하기 때문에 선택적인 의존성에 사용할 수 있지만 실행 중 변경 가능성이 생깁니다.

필드 주입은 코드가 짧지만 Spring Container 없이 객체 생성이 어렵고 테스트나 의존성 파악 측면에서 단점이 있습니다.

그래서 일반적으로 생성자 주입을 우선적으로 사용합니다.

<summary>23. 순환 참조란 무엇인가요?</summary>


### 면접 답변

두 개 이상의 Bean이 서로를 의존하는 구조입니다.

예를 들어 OrderService가 PaymentService를 의존하고 PaymentService가 다시 OrderService를 의존하는 경우입니다.

이런 구조는 객체 책임이 제대로 분리되지 않았다는 신호일 가능성이 높습니다.

단순히 Lazy 주입으로 우회하기보다는 서비스 책임을 재설계하거나 공통 책임을 별도 컴포넌트로 분리하는 것이 좋다고 생각합니다.

### 예상 꼬리질문

* 순환 참조를 `@Lazy`로 해결하는 것은 어떤가요?
* 이벤트 방식으로 해결할 수 있나요?

<details class="interview-question">
<summary>24. 생성자 주입에서 순환 참조가 발생하면 어떻게 되나요?</summary>


### 면접 답변

A가 생성되려면 B가 필요하고 B가 생성되려면 다시 A가 필요한 상황이므로 객체 생성 자체를 완료할 수 없습니다.

따라서 애플리케이션 시작 단계에서 Bean 생성 예외가 발생합니다.

이 문제는 주입 방식만 바꾸는 것보다 두 객체가 서로 강하게 의존하게 된 설계 원인을 확인하는 것이 중요합니다.

### 예상 꼬리질문

* 최근 Spring Boot에서는 순환 참조 기본 설정이 어떻게 되나요?

<summary>25. AOP란 무엇인가요?</summary>


### 면접 답변

AOP는 Aspect-Oriented Programming으로 여러 비즈니스 로직에 반복되는 공통 관심사를 분리하는 프로그래밍 방식입니다.

대표적으로 트랜잭션, 로깅, 권한 확인, 실행 시간 측정 등이 있습니다.

Spring에서는 Proxy를 이용해 대상 객체 호출 전후에 부가 기능을 삽입하는 방식으로 AOP를 제공합니다.

이를 통해 핵심 비즈니스 로직과 공통 인프라 로직을 분리할 수 있습니다.

<summary>26. AOP를 사용하는 대표적인 사례는 무엇인가요?</summary>


### 면접 답변

가장 대표적인 사례는 Spring의 `@Transactional`입니다.

서비스 메서드마다 직접 트랜잭션 시작과 commit, rollback 코드를 작성하는 대신 AOP Proxy가 메서드 호출 전후에 해당 기능을 처리합니다.

그 외에도 API 실행 시간 측정, 감사 로그, 권한 확인처럼 여러 클래스에 반복적으로 적용되는 횡단 관심사에 사용할 수 있습니다.

<summary>27. Aspect, Advice, Join Point, Pointcut을 설명해주세요.</summary>


### 면접 답변

Aspect는 공통 기능 전체를 의미하고 Advice는 실제로 수행될 부가 로직입니다.

Join Point는 Advice를 적용할 수 있는 실행 지점이고 Spring AOP에서는 주로 메서드 실행이 대상입니다.

Pointcut은 여러 Join Point 중 실제로 Advice를 적용할 대상을 선택하는 표현입니다.

예를 들어 특정 패키지의 Service 메서드 실행 시간을 측정하도록 Pointcut을 정의할 수 있습니다.

<summary>28. Spring AOP는 내부적으로 어떻게 동작하나요?</summary>


### 면접 답변

Spring AOP는 일반적으로 대상 객체를 직접 호출하는 대신 Proxy 객체를 Bean으로 제공합니다.

호출자는 Proxy를 호출하고 Proxy가 필요한 Advice를 실행한 다음 실제 대상 객체의 메서드를 호출합니다.

인터페이스 기반이면 JDK Dynamic Proxy를 사용할 수 있고 클래스 기반 Proxy에는 CGLIB 방식이 사용될 수 있습니다.

`@Transactional`이 대표적인 Proxy 기반 기능입니다.

* private method에도 AOP가 적용되나요?

<summary>29. JDK Dynamic Proxy와 CGLIB 차이는 무엇인가요?</summary>


### 면접 답변

JDK Dynamic Proxy는 인터페이스를 기반으로 Proxy 객체를 생성합니다.

CGLIB 기반 Proxy는 대상 클래스를 상속하는 방식으로 Proxy 클래스를 생성하기 때문에 인터페이스가 없어도 사용할 수 있습니다.

클래스 상속 기반이므로 final 클래스나 final 메서드는 Proxy 적용에 제약이 생길 수 있습니다.

<summary>30. Self Invocation에서 AOP가 적용되지 않을 수 있는 이유는 무엇인가요?</summary>


### 면접 답변

Spring AOP는 외부에서 Proxy를 통해 대상 메서드가 호출될 때 동작합니다.

그런데 같은 객체 내부에서 `this.method()` 형태로 다른 메서드를 호출하면 Proxy를 거치지 않고 실제 객체 내부 호출이 이루어집니다.

따라서 내부 메서드에 `@Transactional`이나 AOP 애노테이션이 있어도 기대한 기능이 적용되지 않을 수 있습니다.

이 경우 트랜잭션 경계를 별도 Bean으로 분리하는 방식 등을 고려할 수 있습니다.
