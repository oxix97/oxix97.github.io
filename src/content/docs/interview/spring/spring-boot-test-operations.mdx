<details class="interview-question">
<summary>96. Spring Boot Auto Configuration은 어떻게 동작하나요?</summary>


### 면접 답변

Spring Boot가 현재 Classpath, 설정 값, 이미 등록된 Bean 등을 확인해 필요한 설정과 Bean을 자동으로 등록하는 기능입니다.

예를 들어 특정 라이브러리가 Classpath에 존재하고 사용자가 별도 Bean을 등록하지 않은 경우 기본 설정을 제공할 수 있습니다.

이 과정에는 `@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty` 같은 조건부 설정이 사용됩니다.

개발자가 직접 설정을 제공하면 기본 자동 설정을 대체할 수 있다는 점도 중요합니다.

* `@SpringBootApplication` 안에는 무엇이 들어 있나요?

<details class="interview-question">
<summary>97. `application.yml`과 Profile을 어떻게 활용하나요?</summary>


### 면접 답변

application.yml에는 DB 연결 정보, Server 설정, 외부 API 설정처럼 실행 환경에 필요한 Configuration을 관리할 수 있습니다.

Profile을 사용하면 local, test, prod처럼 환경별로 서로 다른 설정을 적용할 수 있습니다.

다만 비밀번호나 API Key 같은 Secret 값을 Git 저장소에 직접 포함하면 안 되고 환경 변수나 Secret 관리 시스템을 통해 주입하는 방식이 적절합니다.

* `@ConfigurationProperties`와 `@Value` 중 어떤 것을 사용하나요?

<details class="interview-question">
<summary>98. `@SpringBootTest`, `@WebMvcTest`, `@DataJpaTest` 차이는 무엇인가요?</summary>


### 면접 답변

`@SpringBootTest`는 전체 ApplicationContext를 로딩하기 때문에 실제 애플리케이션 구성과 가까운 통합 테스트에 적합하지만 상대적으로 느립니다.

`@WebMvcTest`는 MVC 관련 Bean 중심으로 로딩해 Controller, Validation, HTTP Mapping 등을 테스트할 때 사용합니다.

`@DataJpaTest`는 Repository와 JPA 관련 구성 중심으로 로딩해 Entity Mapping이나 Query 테스트에 적합합니다.

테스트 목적에 필요한 범위만 로딩해서 빠르고 명확한 테스트를 만드는 것이 중요합니다.

### 예상 꼬리질문

* MockMvc는 무엇인가요?

<summary>99. Spring Boot 애플리케이션 장애가 발생하면 어떤 순서로 확인하나요?</summary>


### 면접 답변

먼저 장애 범위와 증상을 확인합니다. 전체 요청 실패인지 특정 API인지, 오류율 증가인지 Latency 문제인지부터 확인하겠습니다.

그다음 애플리케이션 로그와 Metric을 확인해서 Error 증가, Thread Pool, Heap, GC, DB Connection Pool 등의 상태를 봅니다.

DB 관련 문제가 의심되면 Slow Query, Lock, Connection 수, 실행 계획 등을 확인하고 외부 시스템 의존성이 있다면 Timeout과 Error Rate를 확인합니다.

원인을 찾은 뒤에는 임시 대응과 근본 원인 해결을 분리해서 접근하겠습니다.

### 예상 꼬리질문

* 로그부터 볼 건가요 Metric부터 볼 건가요?
* DB Connection Pool 고갈은 어떻게 확인하나요?
* Thread Dump는 언제 확인하나요?


</details>
<details class="interview-question">
<summary>100. Spring Boot 서버의 응답 시간이 갑자기 느려졌다면 어떻게 분석하겠습니까?</summary>


### 면접 답변

먼저 전체 시스템 문제인지 특정 API 문제인지 구분하겠습니다.

Metric을 확인해서 CPU, Memory, GC Pause, Thread Pool, DB Connection Pool, 요청 Latency 변화를 봅니다.

특정 API 문제라면 로그나 Trace를 이용해 Controller, Service, DB, 외부 API 중 어느 구간에서 시간이 증가했는지 분리하겠습니다.

DB가 원인이라면 Slow Query와 실행 계획, Index 사용 여부, Lock 대기를 확인하고 외부 API라면 Timeout과 Connection Pool 상태를 확인하겠습니다.

또한 최근 Deployment나 Configuration 변경이 있었다면 해당 시점과 장애 발생 시점을 비교합니다.

핵심은 바로 코드를 수정하기보다 **Latency를 구간별로 분해해서 병목 위치를 먼저 특정하는 것**이라고 생각합니다.

### 핵심 포인트

`범위 확인 → Metric → Trace/Log → DB → 외부 API → Thread/Connection Pool → 최근 변경`

### 예상 꼬리질문

* CPU는 낮은데 응답이 느리다면 무엇을 의심하나요?
* DB Connection Pool이 부족하면 어떤 증상이 나타나나요?
* GC Pause가 원인인지 어떻게 확인하나요?
* API가 간헐적으로 5초씩 느려진다면 무엇부터 보나요?
* 최근 코드 변경이 없는데 장애가 날 수도 있나요?


</details>
