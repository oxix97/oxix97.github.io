<summary>91. MySQL InnoDB의 Undo Log와 Redo Log 역할은 무엇인가요?</summary>


### 면접 답변

Undo Log는 Transaction Rollback과 MVCC에서 이전 Version을 제공하는 데 사용됩니다.

Redo Log는 Commit된 변경이 실제 Data Page에 아직 반영되지 않았더라도 장애 후 재적용할 수 있도록 변경 정보를 기록합니다.

쉽게 말하면 Undo는 **이전 상태로 되돌리거나 읽기 위한 정보**, Redo는 **Commit된 변경을 복구하기 위한 정보**라고 설명할 수 있습니다.

<summary>92. PostgreSQL WAL이란 무엇인가요?</summary>


### 면접 답변

WAL은 Write-Ahead Logging으로 Data Page를 Disk에 직접 쓰기 전에 변경 로그를 먼저 기록하는 방식입니다.

장애가 발생하면 마지막 Checkpoint 이후 WAL을 Replay해서 Commit된 변경을 복구할 수 있습니다.

WAL은 Durability뿐 아니라 Streaming Replication이나 Point-In-Time Recovery에도 중요한 역할을 합니다.

* WAL이 계속 쌓이면 어떻게 관리하나요?

<summary>93. PostgreSQL에서 VACUUM이 필요한 이유는 무엇인가요?</summary>


### 면접 답변

PostgreSQL MVCC는 UPDATE나 DELETE 시 기존 Tuple Version을 즉시 물리적으로 삭제하지 않습니다.

더 이상 어떤 Transaction에서도 필요하지 않은 Tuple이 Dead Tuple이 되고 이를 정리해 공간을 재사용할 수 있도록 하는 과정이 VACUUM입니다.

또한 Visibility Map을 갱신해 Index Only Scan을 돕고 Transaction ID Wraparound를 방지하는 역할도 합니다. 일반 `VACUUM`은 공간을 Table 내부에서 재사용하게 하며 보통 파일 크기를 운영체제에 바로 반환하지는 않습니다.

### 예상 꼬리질문

* VACUUM과 VACUUM FULL의 차이는 무엇인가요?
* VACUUM이 Table 크기를 OS에 바로 반환하나요?

<summary>94. PostgreSQL Dead Tuple이란 무엇인가요?</summary>


### 면접 답변

UPDATE나 DELETE로 인해 더 이상 현재 데이터 Version으로 사용되지 않고 어떤 활성 Snapshot에서도 필요하지 않게 된 Tuple입니다.

PostgreSQL은 MVCC 때문에 이전 Version을 즉시 제거하지 않으므로 이런 Dead Tuple이 누적될 수 있습니다.

너무 많아지면 Table과 Index Bloat, Scan 비용 증가로 이어질 수 있기 때문에 Autovacuum이 중요합니다.

### 예상 꼬리질문

<summary>95. PostgreSQL Autovacuum이란 무엇인가요?</summary>


### 면접 답변

PostgreSQL이 Table의 변경량을 모니터링해서 필요할 때 `VACUUM`과 `ANALYZE`를 자동 실행하는 백그라운드 기능입니다.

Dead Tuple을 정리하고 Transaction ID Freeze를 수행하며 통계 정보도 적절히 갱신할 수 있습니다.

쓰기 부하가 높은 대형 Table에서는 기본 설정만으로 충분하지 않을 수 있어 Table별 Threshold나 Scale Factor 등을 조정하기도 합니다.

<summary>96. Offset Pagination이 데이터가 많을 때 느려지는 이유는 무엇인가요?</summary>


### 면접 답변

예를 들어 `OFFSET 100000 LIMIT 20`을 실행하면 DB는 일반적으로 앞의 100,000 Row를 결과에서 버리더라도 해당 위치까지 탐색해야 합니다.

Offset이 커질수록 읽어야 할 Row 수가 계속 증가합니다.

또한 페이지 이동 사이에 데이터가 삽입되거나 삭제되면 중복이나 누락이 발생할 수도 있습니다.

<summary>97. Cursor/Keyset Pagination은 어떻게 동작하나요?</summary>


### 면접 답변

마지막으로 조회한 Row의 정렬 Key를 다음 Query의 시작 조건으로 사용하는 방식입니다.

예를 들어 `id < lastId ORDER BY id DESC LIMIT 20`과 같이 조회합니다.

적절한 Index가 있다면 Offset이 아무리 뒤로 가더라도 시작 위치를 빠르게 찾을 수 있어 대용량 데이터에서 효율적입니다.

다만 임의의 100페이지로 바로 이동하기 어렵고 정렬 Key가 고유하지 않다면 추가 Tie-Breaker가 필요합니다.

<summary>98. DB Connection Pool을 사용하는 이유는 무엇인가요?</summary>


### 면접 답변

DB Connection을 생성하고 인증하는 작업은 비용이 크기 때문에 일정 수의 Connection을 미리 만들어 재사용합니다.

애플리케이션은 요청마다 새 Connection을 만들지 않고 Pool에서 빌렸다가 Transaction이 끝나면 반환합니다.

Pool 크기가 너무 작으면 Connection을 기다리는 요청이 늘고, 너무 크면 DB가 동시에 처리해야 하는 Session이 증가해 오히려 성능이 나빠질 수 있습니다.

<summary>99. Unique Constraint를 애플리케이션 중복 검증과 함께 사용하는 이유는 무엇인가요?</summary>


### 면접 답변

애플리케이션의 사전 조회는 사용자에게 빠르고 의미 있는 오류를 반환하는 데 유용하지만 최종 정합성을 보장하지는 못합니다.

두 요청이 동시에 `exists = false`를 확인한 뒤 INSERT하면 둘 다 검증을 통과할 수 있기 때문입니다.

그래서 애플리케이션 검증은 빠른 실패와 사용자 경험을 담당하고 DB Unique Constraint는 Race Condition 상황에서도 최종 중복 저장을 차단하는 마지막 방어선으로 두는 것이 좋습니다.

### 예상 꼬리질문

* Unique Constraint 오류는 어떤 HTTP Status로 반환하나요?
* 먼저 Lock을 잡으면 Unique Constraint는 없어도 되나요?
* 중복 검증과 INSERT를 한 Transaction으로 묶으면 해결되나요?

<details class="interview-question">
<summary>100. 동일 사용자가 동시에 같은 상품을 주문해서 중복 주문이 발생한다면 DB 관점에서 어떻게 해결하겠습니까?</summary>


### 면접 답변

먼저 **비즈니스적으로 무엇을 중복으로 정의하는지 DB 제약으로 표현할 수 있는지** 확인하겠습니다.

예를 들어 동일 `buyer_id + product_id` 조합에서 `PAID`, `CREATED` 같은 활성 주문이 하나만 존재해야 한다면 PostgreSQL에서는 조건부 Unique Index를 이용해서 활성 상태 Row만 대상으로 유일성을 보장할 수 있습니다.

```sql
CREATE UNIQUE INDEX uq_active_order
ON order_product (buyer_id, product_id)
WHERE status IN ('CREATED', 'PAID');
```

이렇게 하면 애플리케이션 요청이 동시에 들어와도 최종 DB 저장 단계에서 하나만 성공합니다.

MySQL에서는 PostgreSQL과 같은 일반적인 Partial Unique Index를 직접 제공하지 않기 때문에 Generated Column을 이용한 Unique Index, 별도 활성 상태 Table, Locking 전략 등 데이터 모델에 맞는 방법을 검토하겠습니다.

애플리케이션에서는 먼저 중복 여부를 조회해서 빠르게 실패시킬 수 있지만 이 조회만으로는 Race Condition을 막지 못합니다.

충돌 요청을 먼저 직렬화할 필요가 있다면 `SELECT FOR UPDATE` 같은 Pessimistic Lock도 고려할 수 있지만 존재하지 않는 Row에 대한 Lock과 Range Lock 동작은 DB별로 주의해야 합니다.

결국 저는 **애플리케이션 검증은 빠른 차단, Lock은 경쟁 구간 제어, Unique Constraint는 최종 정합성 보장**으로 책임을 나눠 설계하겠습니다.

### 핵심 포인트

`Race Condition → DB Constraint → Partial Unique Index → Lock → 최종 정합성`
