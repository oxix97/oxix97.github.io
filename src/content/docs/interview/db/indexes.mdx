질문을 먼저 소리 내어 답한 뒤 펼쳐서 답변과 예상 꼬리질문을 확인한다.

<details class="interview-question">
<summary>31. Index란 무엇인가요?</summary>


### 면접 답변

Index는 Table의 모든 Row를 직접 확인하지 않고 원하는 데이터를 빠르게 찾기 위한 별도의 자료구조입니다.

대표적으로 B-Tree 계열 구조를 사용하며 검색 대상 값과 Row를 찾을 수 있는 정보를 저장합니다.

조회 성능을 높일 수 있지만 저장 공간이 추가로 필요하고 INSERT, UPDATE, DELETE 시 Index도 함께 갱신해야 하는 비용이 있습니다.

### 예상 꼬리질문

* 모든 Column에 Index를 걸면 왜 안 되나요?
* Index가 많으면 어떤 문제가 발생하나요?


</details>
<details class="interview-question">
<summary>32. Index를 사용하는 이유는 무엇인가요?</summary>


### 면접 답변

전체 Table을 순회하는 Full Scan 대신 조건에 맞는 Row 위치를 빠르게 좁힐 수 있기 때문입니다.

특히 데이터가 많고 선택도가 높은 조건에서는 성능 차이가 크게 날 수 있습니다.

또한 적절한 Index는 WHERE뿐 아니라 JOIN, ORDER BY, GROUP BY에도 활용될 수 있습니다.

### 예상 꼬리질문

* 데이터가 적을 때도 Index가 유리한가요?
* Index Scan보다 Full Scan이 빠른 경우도 있나요?


</details>
<details class="interview-question">
<summary>33. Index의 단점은 무엇인가요?</summary>


### 면접 답변

첫 번째로 별도 저장 공간이 필요합니다.

두 번째로 데이터 변경 시 Index 구조도 갱신해야 하기 때문에 INSERT, UPDATE, DELETE 성능에 영향을 줍니다.

세 번째로 Index가 많아지면 Optimizer가 선택해야 할 후보도 늘고 Buffer Cache를 더 많이 차지할 수 있습니다.

따라서 Query 패턴에 실제로 필요한 Index만 만드는 것이 중요합니다.

### 예상 꼬리질문

* 사용하지 않는 Index는 어떻게 찾나요?
* Index를 추가한 뒤 어떤 항목을 모니터링하나요?


</details>
<details class="interview-question">
<summary>34. B-Tree/B+Tree 기반 Index를 많이 사용하는 이유는 무엇인가요?</summary>


### 면접 답변

Tree 높이를 낮게 유지하면서도 정렬된 구조를 제공하기 때문입니다.

한 Node에 많은 Key를 저장할 수 있어 Disk I/O 횟수를 줄일 수 있고, Equality 검색뿐 아니라 Range Query와 정렬에도 사용할 수 있습니다.

실제 DB Index 구현은 일반적인 자료구조 교과서의 B+Tree와 세부 구현이 다를 수 있지만 핵심은 균형 잡힌 정렬 Tree라는 점입니다.

### 예상 꼬리질문

* Binary Search Tree보다 DB에서 B-Tree가 적합한 이유는 무엇인가요?
* Range Scan이 가능한 이유는 무엇인가요?


</details>
<details class="interview-question">
<summary>35. Hash Index와 B-Tree Index의 차이는 무엇인가요?</summary>


### 면접 답변

Hash Index는 Key를 Hash 값으로 변환해 Equality 검색에 강하지만 데이터 정렬 순서를 유지하지 않습니다.

그래서 `<`, `>`, BETWEEN 같은 범위 검색이나 ORDER BY에는 적합하지 않습니다.

B-Tree 계열 Index는 Key가 정렬되어 있기 때문에 Equality뿐 아니라 Range Search와 정렬에도 활용할 수 있어 일반적인 DB Index로 많이 사용됩니다.

### 예상 꼬리질문

* Redis Hash와 DB Hash Index는 같은 개념인가요?
* PostgreSQL에서도 Hash Index를 지원하나요?


</details>
<details class="interview-question">
<summary>36. Clustered Index와 Non-Clustered Index의 차이는 무엇인가요?</summary>


### 면접 답변

Clustered Index는 Index의 Key 순서와 실제 Row 저장 구조가 밀접하게 연결되어 있는 형태입니다.

MySQL InnoDB에서는 Primary Key B+Tree의 Leaf Page 자체에 Row 데이터가 저장됩니다.

반면 Secondary Index는 별도의 Index 구조를 가지며 MySQL InnoDB에서는 Leaf에 Primary Key 값을 저장해 다시 Clustered Index를 찾아갑니다.

PostgreSQL은 기본적으로 Heap Table과 Index가 분리되어 있기 때문에 MySQL InnoDB와 같은 의미의 상시 Clustered Index 구조는 아닙니다.

### 예상 꼬리질문

* 한 Table에 Clustered Index가 여러 개 있을 수 있나요?
* PostgreSQL의 CLUSTER 명령은 무엇인가요?


</details>
<details class="interview-question">
<summary>37. MySQL InnoDB Primary Key Index 구조를 설명해주세요.</summary>


### 면접 답변

InnoDB에서는 Primary Key를 기준으로 B+Tree 형태의 Clustered Index를 구성합니다.

Leaf Node에 Primary Key뿐 아니라 해당 Row의 실제 데이터가 저장됩니다.

따라서 PK Range 조회가 효율적이고, PK 자체가 Row 저장 위치를 결정하는 중요한 기준이 됩니다.

Primary Key가 없다면 InnoDB는 모든 Key Column이 `NOT NULL`인 첫 번째 Unique Index를 Clustered Index로 사용합니다. 그런 Index도 없으면 6바이트 내부 Row ID를 가진 숨은 Clustered Index를 생성합니다.

### 예상 꼬리질문

* UUID PK가 문제될 수 있는 이유는 무엇인가요?
* Auto Increment PK가 유리한 점은 무엇인가요?


</details>
<details class="interview-question">
<summary>38. MySQL InnoDB Secondary Index는 데이터를 어떻게 찾나요?</summary>


### 면접 답변

Secondary Index의 Leaf에는 일반적으로 Secondary Key와 해당 Row의 Primary Key가 저장됩니다.

Secondary Index로 조건에 맞는 PK를 찾은 뒤 실제 Row의 다른 Column이 필요하면 다시 Primary Key Clustered Index를 탐색합니다.

즉 Secondary Index 탐색 뒤 Clustered Index를 한 번 더 찾는 추가 Lookup이 발생합니다.

하지만 필요한 Column이 모두 Secondary Index 안에 있다면 Covering Index가 되어 추가 PK Lookup을 피할 수 있습니다.

### 예상 꼬리질문

* Secondary Index에 PK가 포함되는 이유는 무엇인가요?
* PK가 길면 Secondary Index에 어떤 영향이 있나요?


</details>
<details class="interview-question">
<summary>39. PostgreSQL의 Heap Table과 Index 관계를 설명해주세요.</summary>


### 면접 답변

PostgreSQL은 기본적으로 Table Row를 Heap에 저장하고 Index는 별도 구조로 유지합니다.

B-Tree Index Entry는 Heap의 Tuple 위치를 가리키는 TID 같은 정보를 가지고 있습니다.

따라서 Index Scan을 하면 Index에서 후보를 찾은 뒤 Heap에 접근해서 Row의 Visibility 등을 확인할 수 있습니다.

조건이 맞으면 Visibility Map을 이용해 Heap 접근을 줄이는 Index Only Scan이 가능할 수 있습니다.

### 예상 꼬리질문

* PostgreSQL Index Only Scan은 왜 항상 Heap 접근을 피하지 못하나요?
* Visibility Map이 무엇인가요?


</details>
<details class="interview-question">
<summary>40. Composite Index란 무엇인가요?</summary>


### 면접 답변

두 개 이상의 Column을 하나의 Index로 구성한 것입니다.

예를 들어 `(user_id, created_at)` Index를 만들면 특정 사용자의 주문을 날짜순으로 조회하는 Query에 유용할 수 있습니다.

하지만 Composite Index는 Column 순서에 따라 활용 가능한 Query가 달라지기 때문에 단순히 조건에 등장하는 Column을 모두 넣는 방식으로 만들면 안 됩니다.

### 예상 꼬리질문

* `(A, B)`와 `(B, A)`는 같은 Index인가요?
* Composite Index 순서는 어떻게 결정하나요?


</details>
<details class="interview-question">
<summary>41. Composite Index에서 Column 순서가 중요한 이유는 무엇인가요?</summary>


### 면접 답변

B-Tree Index가 첫 번째 Column부터 정렬된 구조를 가지기 때문입니다.

예를 들어 `(user_id, created_at)`은 먼저 user_id로 정렬되고 동일 user_id 안에서 created_at으로 정렬됩니다.

따라서 `user_id = ? AND created_at > ?` 같은 Query에 효과적이지만 created_at만 검색하는 Query에서는 효율이 크게 떨어질 수 있습니다.

일반적으로 Equality 조건, Range 조건, 정렬 요구사항과 Cardinality를 함께 보고 순서를 결정합니다.

### 예상 꼬리질문

* Cardinality가 높은 Column을 항상 앞에 두나요?
* Equality와 Range가 같이 있다면 어떤 순서가 좋나요?


</details>
<details class="interview-question">
<summary>42. `(A, B)` Index가 있을 때 B만 조건에 사용하면 어떻게 되나요?</summary>


### 면접 답변

일반적인 B-Tree Index에서는 첫 번째 Column A 조건이 없으면 B만으로 효율적인 범위를 바로 찾기 어렵습니다.

따라서 Index 전체를 많이 읽거나 Optimizer가 Full Scan을 선택할 수 있습니다.

다만 DB의 기능과 통계에 따라 Skip Scan 같은 최적화를 사용할 수 있는 경우가 있으므로 절대적으로 "Index를 전혀 사용하지 않는다"고 단정하면 안 됩니다.

### 예상 꼬리질문

* Leftmost Prefix Rule이 무엇인가요?
* Skip Scan은 무엇인가요?


</details>
<details class="interview-question">
<summary>43. Leftmost Prefix Rule이란 무엇인가요?</summary>


### 면접 답변

Composite B-Tree Index가 앞쪽 Column부터 순서대로 활용되는 특성을 의미합니다.

예를 들어 `(A, B, C)` Index라면 A, A+B, A+B+C 형태의 조건은 효율적으로 활용하기 쉽습니다.

하지만 선두 Column A가 빠지면 후속 Column의 정렬 구조를 바로 활용하기 어렵습니다.

Range 조건이 중간에 들어가면 그 이후 Column의 Index 활용 방식도 제한될 수 있습니다.

### 예상 꼬리질문

* `(A = ?, B > ?, C = ?)`라면 C도 Index에 사용되나요?
* Index Condition Pushdown은 무엇인가요?


</details>
<details class="interview-question">
<summary>44. Covering Index란 무엇인가요?</summary>


### 면접 답변

Query에 필요한 모든 Column이 하나의 Index 안에 포함되어 있어 실제 Table Row를 추가로 읽지 않고 Index만으로 결과를 반환할 수 있는 경우입니다.

MySQL에서는 Secondary Index에서 Clustered Index로 다시 접근하는 비용을 줄일 수 있고 PostgreSQL에서는 조건이 맞으면 Index Only Scan이 가능합니다.

다만 Covering을 만들기 위해 지나치게 많은 Column을 Index에 넣으면 Index 크기와 쓰기 비용이 증가합니다.

### 예상 꼬리질문

* PostgreSQL의 INCLUDE는 무엇인가요?
* 모든 SELECT Column을 Index에 넣으면 좋은가요?


</details>
<details class="interview-question">
<summary>45. Index Scan과 Full Table Scan의 차이는 무엇인가요?</summary>


### 면접 답변

Index Scan은 Index를 이용해 필요한 Row 후보를 좁힌 뒤 데이터를 읽는 방식입니다.

Full Table Scan은 Table의 많은 또는 모든 Page를 순차적으로 읽습니다.

조건에 해당하는 Row가 매우 많다면 Index를 통해 개별 Row를 랜덤 접근하는 것보다 Sequential Scan이 더 빠를 수도 있습니다.

그래서 Index가 존재한다고 항상 Index Scan이 선택되는 것은 아닙니다.

### 예상 꼬리질문

* 몇 퍼센트 이상이면 Full Scan이 유리한가요?
* Optimizer는 어떤 통계를 사용하나요?


</details>
<details class="interview-question">
<summary>46. Index가 있는데도 사용되지 않는 이유는 무엇인가요?</summary>


### 면접 답변

조건의 선택도가 낮아 Table 대부분을 읽어야 하거나, Index 선두 Column 조건이 없거나, Column에 함수나 형변환이 적용된 경우 등이 있습니다.

또는 Table이 작아서 Full Scan이 더 저렴하다고 Optimizer가 판단할 수도 있습니다.

통계 정보가 오래되어 잘못된 비용 계산을 하는 경우도 있습니다.

따라서 Index 사용 여부는 Query 형태와 실행 계획을 함께 봐야 합니다.

### 예상 꼬리질문

* Index Hint를 사용하는 것은 좋은가요?
* 통계 정보는 어떻게 갱신하나요?

<summary>47. LIKE 검색에서 Index를 사용할 수 있는 경우와 없는 경우는 무엇인가요?</summary>


### 면접 답변

일반적인 B-Tree Index에서는 `'abc%'`처럼 Prefix가 고정된 검색은 범위 검색으로 활용할 수 있는 경우가 많습니다.

반면 `'%abc'`처럼 앞부분이 Wildcard면 Index 시작 위치를 특정할 수 없어 일반 B-Tree Index 활용이 어렵습니다.

전문 검색이나 부분 문자열 검색이 중요하면 PostgreSQL의 trigram Index나 별도의 Search Engine 등을 검토할 수 있습니다.

### 예상 꼬리질문

* `%abc%` 검색을 빠르게 하려면 어떻게 하나요?
* Full Text Search란 무엇인가요?

<summary>48. 함수가 적용된 Column에서 Index 사용이 어려울 수 있는 이유는 무엇인가요?</summary>


### 면접 답변

일반 Index가 원래 Column 값을 기준으로 정렬되어 있는데 `LOWER(name)`이나 `DATE(created_at)`처럼 변환된 값을 조건으로 사용하면 기존 Index 순서를 직접 활용하기 어려울 수 있습니다.

이를 SARGable하지 않은 조건이라고 표현하기도 합니다.

DB가 지원한다면 Functional Index 또는 Expression Index를 만들어 해결할 수 있습니다.

<summary>49. Cardinality란 무엇이며 Index와 어떤 관계가 있나요?</summary>


### 면접 답변

Cardinality는 일반적으로 Column에서 서로 다른 값의 개수를 의미합니다.

값이 다양할수록 특정 조건으로 Row를 좁히기 쉬우므로 Index의 선택도가 좋아질 가능성이 있습니다.

하지만 Cardinality가 높다고 항상 Index 선두 Column으로 넣어야 하는 것은 아니고 실제 Query의 Equality, Range, Join, 정렬 조건을 함께 봐야 합니다.

### 예상 꼬리질문

* Selectivity와 Cardinality의 차이는 무엇인가요?
* Boolean Column Index는 무조건 의미가 없나요?


</details>
<details class="interview-question">
<summary>50. 성별처럼 Cardinality가 낮은 Column에 Index를 만드는 것이 왜 효과가 낮을 수 있나요?</summary>


### 면접 답변

값 종류가 적으면 하나의 조건에 해당하는 Row가 Table의 상당 부분을 차지할 가능성이 높습니다.

이 경우 Index를 통해 수많은 Row를 찾아 Table을 랜덤 접근하는 것보다 Full Scan이 더 저렴할 수 있습니다.

하지만 부분 Index나 다른 Column과 Composite Index로 묶는 등 Query 패턴에 따라 충분히 유용할 수도 있습니다.

* PostgreSQL Partial Index를 활용할 수 있나요?
* `status = 'ACTIVE'` 조건에는 어떻게 Index를 설계하나요?
