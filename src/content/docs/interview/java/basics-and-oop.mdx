<summary>1. Java의 특징을 설명해주세요.</summary>


### 면접 답변

Java는 JVM 위에서 실행되는 객체지향 언어입니다. Java 코드는 컴파일 후 JVM이 이해할 수 있는 바이트코드로 변환되기 때문에 운영체제마다 JVM만 제공된다면 같은 바이트코드를 실행할 수 있다는 장점이 있습니다.

또한 Garbage Collection을 통해 메모리를 자동 관리하고, 정적 타입 시스템을 사용해 컴파일 시점에 많은 오류를 확인할 수 있습니다. 멀티스레딩을 언어와 표준 라이브러리 수준에서 지원하며, Spring과 같은 성숙한 생태계가 있다는 점도 서버 개발에서 Java가 많이 사용되는 이유라고 생각합니다.

<summary>2. JVM, JRE, JDK의 차이는 무엇인가요?</summary>


### 면접 답변

JVM은 Java 바이트코드를 실제 머신에서 실행하는 가상 머신입니다.

JRE는 Java 프로그램을 실행하기 위한 환경으로 JVM과 Java 표준 라이브러리 등을 포함합니다.

JDK는 Java 애플리케이션을 개발하기 위한 도구 모음으로, 실행 환경뿐 아니라 `javac`, `javadoc`, `jdb` 같은 컴파일 및 개발 도구까지 포함합니다.

정리하면 **JDK가 개발 환경, JVM이 실제 바이트코드 실행 엔진**이라고 이해하고 있습니다.

최근 Java 배포판에서는 별도의 JRE 패키지를 제공하지 않는 경우도 있지만 개념적인 구분은 이렇게 할 수 있습니다.

### 예상 꼬리질문

* JVM 내부에서는 바이트코드를 어떻게 실행하나요?
* JIT Compiler는 무엇인가요?

<summary>3. Java가 플랫폼 독립적이라고 하는 이유는 무엇인가요?</summary>


### 면접 답변

Java 소스코드를 특정 CPU의 머신 코드로 직접 컴파일하는 것이 아니라 JVM이 실행할 수 있는 바이트코드로 컴파일하기 때문입니다.

예를 들어 macOS에서 생성한 `.class` 파일도 Windows나 Linux에 해당 환경용 JVM이 설치되어 있다면 동일하게 실행할 수 있습니다.

그래서 Java에서는 흔히 **Write Once, Run Anywhere**라는 표현을 사용합니다.

다만 JVM 자체는 운영체제와 CPU 아키텍처에 맞게 구현되어야 하기 때문에 JVM까지 플랫폼 독립적인 것은 아닙니다.

<summary>4. Java의 컴파일과 실행 과정을 설명해주세요.</summary>


### 면접 답변

먼저 `.java` 소스 파일을 `javac` 컴파일러가 `.class` 바이트코드로 변환합니다.

애플리케이션을 실행하면 ClassLoader가 필요한 클래스를 JVM에 로딩하고, JVM은 바이트코드를 검증한 뒤 실행합니다.

초기에는 Interpreter가 바이트코드를 한 줄씩 실행할 수 있고, 반복적으로 실행되는 Hot Spot 코드의 경우 JIT Compiler가 Native Code로 컴파일해서 성능을 높입니다.

실행 중 생성된 객체는 Heap에 저장되고, 더 이상 접근할 수 없는 객체는 Garbage Collector가 회수합니다.

<summary>5. 객체지향 프로그래밍이란 무엇인가요?</summary>


### 면접 답변

객체지향 프로그래밍은 프로그램을 데이터와 행동을 가진 객체들의 협력으로 구성하는 방식입니다.

객체가 자신의 상태와 관련된 행동을 함께 관리하도록 만들어 책임을 적절하게 분리할 수 있습니다.

대표적인 특징으로 캡슐화, 추상화, 상속, 다형성이 있습니다.

제가 중요하다고 생각하는 부분은 단순히 클래스를 많이 만드는 것이 아니라 **변경되는 이유와 책임을 기준으로 객체를 나누고 객체 간 결합도를 낮추는 것**입니다.

<summary>6. 객체지향의 4가지 특징을 설명해주세요.</summary>


### 면접 답변

첫 번째는 **캡슐화**로 객체의 내부 상태와 구현을 숨기고 필요한 인터페이스만 공개하는 것입니다.

두 번째는 **추상화**로 복잡한 내부 구현에서 중요한 특성만 외부에 표현하는 것입니다.

세 번째는 **상속**으로 기존 클래스의 특성을 재사용하거나 확장할 수 있습니다.

마지막은 **다형성**으로 동일한 인터페이스를 사용하면서 실제 구현체에 따라 다른 동작을 수행할 수 있습니다.

특히 Spring에서는 인터페이스와 DI를 통해 다형성을 적극 활용한다고 볼 수 있습니다.

<summary>7. 캡슐화란 무엇이고 왜 필요한가요?</summary>


### 면접 답변

캡슐화는 객체 내부의 상태와 구현 세부 사항을 외부에 직접 노출하지 않고 객체가 제공하는 메서드를 통해 접근하도록 만드는 것입니다.

예를 들어 `balance`를 public으로 노출하기보다 `withdraw()` 같은 메서드에서 잔액 검증까지 수행하도록 만들 수 있습니다.

이렇게 하면 객체 스스로 자신의 불변식을 유지할 수 있고 내부 구현을 변경해도 외부 코드가 받는 영향을 줄일 수 있습니다.

따라서 캡슐화의 핵심 목적은 단순히 `private`을 사용하는 것이 아니라 **변경 영향을 제한하고 객체의 상태를 안전하게 관리하는 것**이라고 생각합니다.

### 예상 꼬리질문

* getter/setter를 모두 제공하면 캡슐화가 된 것인가요?
* DTO에는 왜 getter를 많이 사용하나요?
* 불변식이란 무엇인가요?

<summary>8. 상속의 장점과 단점은 무엇인가요?</summary>


### 면접 답변

상속은 부모 클래스의 기능을 재사용하고 다형성을 활용할 수 있다는 장점이 있습니다.

하지만 자식 클래스가 부모의 구현에 강하게 의존하기 때문에 부모 코드 변경이 자식 클래스에 영향을 미칠 수 있습니다. 또한 상속 관계가 깊어지면 실제 동작을 이해하기 어려워질 수 있습니다.

그래서 단순한 코드 재사용이 목적이라면 상속보다는 **Composition, 즉 객체를 멤버로 가지고 위임하는 방식**을 우선적으로 고려하는 것이 좋다고 생각합니다.

상속은 명확한 `is-a` 관계가 존재할 때 사용하는 것이 적절합니다.

### 면접 답변

다형성은 동일한 타입이나 인터페이스를 통해 여러 구현체를 사용할 수 있는 성질입니다.

이를 통해 구현체가 변경되어도 사용하는 쪽의 코드를 최소한으로 변경할 수 있습니다.

Spring의 DI 역시 인터페이스와 여러 구현체를 조합해 이러한 다형성을 활용하는 대표적인 예입니다.

<summary>10. 추상화란 무엇인가요?</summary>


### 면접 답변

추상화는 복잡한 구현 세부사항을 숨기고 사용자가 필요한 핵심적인 기능만 노출하는 것입니다.

다만 지나친 추상화는 코드 구조를 복잡하게 만들 수 있기 때문에 실제로 변경 가능성이 있거나 책임을 분리할 필요가 있는 지점을 중심으로 적용해야 합니다.

<summary>12. 인스턴스 변수와 클래스 변수의 차이는 무엇인가요?</summary>


### 면접 답변

인스턴스 변수는 각각의 객체가 별도로 가지는 상태입니다.

반면 클래스 변수는 `static`을 붙여 선언하며 특정 객체가 아닌 클래스 자체에 속하기 때문에 모든 인스턴스가 하나의 값을 공유합니다.

예를 들어 사용자의 이름은 인스턴스마다 달라야 하지만 전체 객체에서 공통으로 사용하는 상수나 상태는 static으로 표현할 수 있습니다.

다만 mutable한 static 변수는 전역 상태가 되어 동시성이나 테스트 문제를 만들 수 있기 때문에 신중하게 사용해야 합니다.

<summary>13. static 키워드의 의미를 설명해주세요.</summary>


### 면접 답변

`static`은 특정 객체 인스턴스가 아니라 클래스 자체에 속하는 멤버를 정의할 때 사용합니다.

static 메서드는 객체를 생성하지 않고 클래스 이름으로 호출할 수 있고, static 변수는 해당 클래스의 모든 객체가 공유합니다.

예를 들어 상태를 가지지 않는 유틸리티 함수나 상수를 표현할 때 자주 사용합니다.

다만 static 메서드 내부에서는 특정 객체가 존재하지 않기 때문에 일반 인스턴스 변수나 메서드에 직접 접근할 수 없습니다.

<summary>14. final 키워드는 각각 어떻게 동작하나요?</summary>


### 면접 답변

변수에 `final`을 붙이면 한 번 할당한 뒤 다른 값을 다시 할당할 수 없습니다.

참조형 변수라면 참조 자체를 변경하지 못할 뿐이고 참조하는 객체 내부 상태까지 불변이 되는 것은 아닙니다.

메서드에 final을 붙이면 자식 클래스에서 오버라이딩할 수 없고, 클래스에 붙이면 해당 클래스를 상속할 수 없습니다.

따라서 `final`은 변경 가능성을 제한해 코드의 의도를 명확하게 표현하는 데 사용할 수 있습니다.

<summary>15. this와 super의 차이는 무엇인가요?</summary>


### 면접 답변

`this`는 현재 객체 자신을 가리키고 `super`는 현재 객체의 부모 클래스 영역을 가리킵니다.

`this.field`를 사용하면 현재 인스턴스의 필드를 명확하게 지정할 수 있고 `this()`를 이용하면 같은 클래스의 다른 생성자를 호출할 수 있습니다.

`super.field`나 `super.method()`는 부모 클래스의 멤버에 접근할 때 사용하고, `super()`는 부모 클래스의 생성자를 호출합니다.

### 예상 꼬리질문

* 생성자에서 `this()`와 `super()`를 같이 사용할 수 있나요?
* 부모 생성자는 언제 호출되나요?
* static 메서드에서 this를 사용할 수 있나요?

<summary>16. 생성자의 역할은 무엇인가요?</summary>


### 면접 답변

생성자는 객체가 생성될 때 필요한 초기 상태를 설정하는 역할을 합니다.

특히 객체가 정상적인 상태로 존재하기 위해 필수적인 값을 생성자를 통해 받으면 불완전한 객체가 만들어지는 것을 방지할 수 있습니다.

예를 들어 Order가 반드시 buyerId를 가져야 한다면 생성자에서 buyerId를 받도록 만들 수 있습니다.

Spring에서도 필수 의존성을 명확하게 표현할 수 있기 때문에 생성자 주입이 권장됩니다.

### 예상 꼬리질문

* 생성자는 상속되나요?
* private 생성자는 언제 사용하나요?
* 생성자에서 비즈니스 로직을 수행해도 되나요?

<summary>17. 기본 생성자는 언제 자동으로 생성되나요?</summary>


### 면접 답변

클래스에 개발자가 생성자를 하나도 선언하지 않은 경우 컴파일러가 파라미터가 없는 기본 생성자를 자동으로 만들어줍니다.

하지만 파라미터가 있는 생성자를 하나라도 직접 선언하면 기본 생성자는 자동으로 생성되지 않습니다.

따라서 JPA처럼 기본 생성자를 필요로 하는 기술에서는 별도로 기본 생성자를 선언해야 할 수 있습니다.

<summary>18. 오버로딩과 오버라이딩의 차이는 무엇인가요?</summary>


### 면접 답변

오버로딩은 동일한 클래스에서 같은 이름의 메서드를 파라미터 타입이나 개수를 다르게 정의하는 것입니다. 어떤 메서드를 호출할지는 컴파일 시점에 결정됩니다.

오버라이딩은 부모 클래스나 인터페이스에서 정의한 메서드를 자식 클래스가 동일한 시그니처로 다시 구현하는 것입니다.

오버라이딩은 실제 객체 타입에 따라 런타임에 호출 메서드가 결정되기 때문에 다형성을 구현하는 중요한 방법입니다.

### 예상 꼬리질문

* private 메서드를 오버라이딩할 수 있나요?

<summary>19. 인터페이스와 추상 클래스의 차이는 무엇인가요?</summary>


### 면접 답변

인터페이스는 객체가 제공해야 하는 역할이나 계약을 정의하는 데 주로 사용하고, 추상 클래스는 공통 상태나 구현까지 함께 공유해야 할 때 사용할 수 있습니다.

Java에서는 클래스는 하나의 클래스만 상속할 수 있지만 여러 인터페이스를 구현할 수 있습니다.

인터페이스에도 default method나 static method를 정의할 수 있지만 기본적으로 구현보다는 역할을 추상화하는 목적이 강합니다.

따라서 서로 다른 계층의 객체들이 동일한 기능을 제공해야 한다면 인터페이스를, 공통 상태와 구현을 공유하는 명확한 상속 관계라면 추상 클래스를 고려하겠습니다.

### 예상 꼬리질문

<summary>20. 인터페이스를 사용하는 이유는 무엇인가요?</summary>


### 면접 답변

가장 큰 이유는 호출하는 코드와 실제 구현을 분리하기 위해서입니다.

클라이언트가 구체 클래스가 아니라 인터페이스에 의존하면 구현체를 변경하거나 테스트 구현체로 교체해도 클라이언트 코드에 미치는 영향을 줄일 수 있습니다.

Spring의 DI 역시 이런 구조를 쉽게 만들 수 있도록 지원합니다.

다만 구현체가 하나이고 변경 가능성이나 경계를 둘 필요가 없는 경우까지 무조건 인터페이스를 만드는 것은 오히려 복잡도를 높일 수 있다고 생각합니다.

### 예상 꼬리질문

* 구현체가 하나여도 인터페이스가 필요한 경우는 언제인가요?
* Port-Adapter 구조에서는 인터페이스를 어떻게 사용하나요?
