<summary>41. Java Collection Framework를 설명해주세요.</summary>


### 면접 답변

Java Collection Framework는 여러 데이터를 효율적으로 저장하고 처리하기 위한 인터페이스와 구현체의 집합입니다.

대표적으로 List, Set, Queue가 Collection 인터페이스를 기반으로 하고, Map은 별도의 계층을 가집니다.

List는 순서와 중복을 허용하고 Set은 중복을 허용하지 않으며 Map은 Key-Value 형태로 데이터를 관리합니다.

각 구현체마다 시간 복잡도와 정렬 여부, 동시성 특성이 다르기 때문에 사용 목적에 맞게 선택해야 합니다.

<summary>42. List, Set, Map의 차이는 무엇인가요?</summary>


### 면접 답변

List는 데이터의 순서를 유지하고 중복을 허용합니다.

Set은 데이터 중복을 허용하지 않는 것이 핵심 특성입니다.

Map은 Key와 Value 쌍으로 데이터를 저장하며 Key는 중복될 수 없습니다.

예를 들어 순서가 있는 주문 목록이라면 List, 중복 없는 권한 목록이라면 Set, ID를 통해 빠르게 객체를 찾아야 한다면 Map을 고려할 수 있습니다.

<summary>43. ArrayList와 LinkedList의 차이는 무엇인가요?</summary>


### 면접 답변

ArrayList는 내부적으로 배열을 사용하기 때문에 인덱스를 이용한 조회가 O(1)로 빠릅니다.

하지만 중간 위치에 데이터를 삽입하거나 삭제하면 이후 원소를 이동해야 하기 때문에 O(n)이 될 수 있습니다.

LinkedList는 각 노드가 이전과 다음 노드를 참조하는 구조입니다. 위치를 이미 알고 있다면 연결 변경 자체는 빠르지만 특정 인덱스를 찾으려면 순회가 필요합니다.

실제로는 캐시 지역성과 메모리 효율 등의 이유로 일반적인 목록에서는 ArrayList가 더 많이 사용됩니다.

<summary>44. ArrayList의 내부 구조를 설명해주세요.</summary>


### 면접 답변

ArrayList는 내부적으로 객체 참조를 저장하는 배열을 사용합니다.

`get(index)`를 호출하면 배열의 특정 위치에 바로 접근할 수 있기 때문에 O(1)입니다.

데이터를 추가하다가 내부 배열의 capacity가 부족해지면 더 큰 배열을 생성하고 기존 데이터를 복사합니다.

따라서 조회가 많고 순차적으로 데이터를 추가하는 일반적인 경우에 효율적인 자료구조입니다.

<summary>45. ArrayList에 데이터가 계속 추가되면 어떤 일이 발생하나요?</summary>


### 면접 답변

현재 내부 배열의 capacity보다 데이터가 많아지면 더 큰 배열을 새로 생성하고 기존 원소를 복사합니다.

데이터 크기를 미리 알고 있다면 초기 capacity를 적절하게 지정해 resize를 줄일 수도 있습니다.

<summary>46. HashMap의 내부 구조를 설명해주세요.</summary>


### 면접 답변

HashMap은 내부적으로 bucket 배열을 가지고 Key의 hashCode를 기반으로 저장할 bucket을 결정합니다.

동일한 bucket에 여러 Key가 들어오면 충돌이 발생하며 Java 8 기준으로 처음에는 연결 구조를 사용하고 충돌이 충분히 많아지면 조건에 따라 Red-Black Tree로 전환할 수 있습니다.

조회할 때는 먼저 hash를 이용해 bucket을 찾고 해당 bucket 안에서 equals를 사용해 실제 Key를 찾습니다.

평균적인 조회와 삽입은 O(1)이지만 해시 충돌이 많으면 성능이 저하될 수 있습니다.

<summary>47. HashMap에서 값을 조회하는 과정을 설명해주세요.</summary>


### 면접 답변

먼저 Key의 `hashCode()`를 기반으로 HashMap 내부에서 추가적인 hash 계산을 하고 이를 이용해 bucket index를 결정합니다.

해당 bucket이 비어 있으면 값이 없는 것이고, 데이터가 있다면 hash 값과 equals를 비교해 같은 Key인지 확인합니다.

충돌이 있어 여러 노드가 존재한다면 연결 구조나 트리 구조를 탐색합니다.

따라서 HashMap Key는 hashCode와 equals가 일관되게 구현되어 있어야 합니다.

<summary>48. Hash Collision이 발생하면 어떻게 처리되나요?</summary>


### 면접 답변

서로 다른 Key가 동일한 bucket 위치에 저장되는 상황을 Hash Collision이라고 합니다.

Java HashMap에서는 충돌한 데이터를 하나의 bucket 안에서 관리합니다.

Java 8 이후에는 기본적으로 연결 구조로 관리하다가 충돌이 일정 수준 이상이고 전체 capacity도 충분히 크면 Red-Black Tree로 변경합니다.

이를 통해 최악의 조회 성능이 지나치게 떨어지는 것을 완화합니다.

<summary>49. HashMap의 Key로 mutable 객체를 사용하면 어떤 문제가 발생하나요?</summary>


### 면접 답변

HashMap에 객체를 Key로 넣은 후 equals나 hashCode 계산에 사용하는 필드가 변경되면 문제가 발생할 수 있습니다.

저장 당시 hashCode를 기준으로 특정 bucket에 들어갔는데 이후 hashCode가 변경되면 조회할 때 다른 bucket을 찾게 됩니다.

결과적으로 Map 안에 데이터가 존재하지만 `get()`으로 찾지 못할 수 있습니다.

그래서 HashMap의 Key는 가능하면 String이나 불변 Value Object처럼 immutable한 객체를 사용하는 것이 안전합니다.

<summary>50. HashMap과 ConcurrentHashMap의 차이는 무엇인가요?</summary>


### 면접 답변

HashMap은 기본적으로 thread-safe하지 않기 때문에 여러 스레드가 동시에 수정하면 안전하지 않습니다.

ConcurrentHashMap은 멀티스레드 환경에서 동시 접근을 고려해 설계된 Map입니다.

Java 8 이후 ConcurrentHashMap은 전체 Map에 하나의 lock을 거는 방식보다는 CAS와 bucket 단위 동기화 등을 이용해 동시성을 높입니다.

또한 null Key와 null Value를 허용하지 않는다는 차이도 있습니다.

### 예상 꼬리질문

* `Collections.synchronizedMap()`과 차이는 무엇인가요?
* ConcurrentHashMap의 get에도 lock이 필요한가요?
* null을 허용하지 않는 이유는 무엇인가요?



</details>

<summary>51. HashMap과 Hashtable의 차이는 무엇인가요?</summary>


### 면접 답변

HashMap은 기본적으로 동기화를 제공하지 않지만 Hashtable은 주요 메서드가 synchronized되어 있습니다.

따라서 Hashtable은 thread-safe하지만 전체적인 동시성 측면에서 현대적인 ConcurrentHashMap보다 효율이 떨어질 수 있습니다.

또한 HashMap은 null Key 하나와 null Value를 허용하지만 Hashtable은 null을 허용하지 않습니다.

현재 새로운 코드에서는 Hashtable보다 ConcurrentHashMap을 사용하는 경우가 일반적입니다.

이 때문에 HashSet에 사용자 정의 객체를 저장할 때도 equals와 hashCode 구현이 중요합니다.

<summary>53. TreeMap과 HashMap의 차이는 무엇인가요?</summary>


### 면접 답변

HashMap은 해시 기반으로 구현되어 평균 조회와 삽입이 O(1)이지만 Key의 정렬 순서를 보장하지 않습니다.

TreeMap은 Red-Black Tree 기반으로 Key를 정렬된 상태로 유지하며 조회와 삽입이 O(log n)입니다.

따라서 단순 빠른 조회가 중요하면 HashMap을, 정렬된 Key 순회나 범위 검색이 필요하면 TreeMap을 고려할 수 있습니다.

TreeMap의 Key는 Comparable을 구현하거나 Comparator를 제공해야 합니다.

<summary>55. Comparable과 Comparator의 차이는 무엇인가요?</summary>


### 면접 답변

Comparable은 객체 클래스 자체에 기본 정렬 기준을 정의하는 방식이고 `compareTo()`를 구현합니다.

Comparator는 클래스 외부에서 별도의 정렬 기준을 정의하며 `compare()`를 구현합니다.

예를 들어 User의 기본 정렬을 ID 순으로 정의한다면 Comparable을 사용할 수 있고, 나이순이나 이름순처럼 여러 정렬 방식이 필요하면 Comparator가 더 유연합니다.

<summary>57. fail-fast와 fail-safe의 차이는 무엇인가요?</summary>


### 면접 답변

일반적인 ArrayList의 Iterator는 순회 중 구조적인 변경을 감지하면 빠르게 `ConcurrentModificationException`을 발생시키는데 이를 fail-fast라고 합니다.

ConcurrentHashMap처럼 동시성을 고려한 Collection은 순회 중 수정이 발생해도 예외를 발생시키지 않고 약하게 일관된 결과를 제공하는 경우가 있습니다.

보통 이를 fail-safe라고 표현하지만 Java 공식 API 용어라기보다는 관행적인 표현에 가깝습니다.

### 예상 꼬리질문

Stream을 사용해 삭제할 원소를 제외한 새로운 Collection을 만드는 방법도 있습니다.

어떤 방식을 사용할지는 원본 Collection을 수정할 것인지 여부에 따라 결정할 수 있습니다.

<summary>59. Collections.unmodifiableList()와 Immutable Collection의 차이는 무엇인가요?</summary>


### 면접 답변

`Collections.unmodifiableList()`는 기존 List를 수정할 수 없는 View로 감싸는 방식입니다.

해당 View를 통해서는 수정할 수 없지만 원본 List가 변경되면 View에서도 변경된 내용이 보일 수 있습니다.

반면 `List.of()`처럼 생성한 immutable collection은 구조 자체를 변경할 수 없습니다.

따라서 외부 변경까지 막고 싶은 경우 원본 데이터의 방어적 복사까지 고려해야 합니다.

### 예상 꼬리질문

* List 내부 객체가 mutable하면 어떻게 되나요?
* `List.copyOf()`는 어떤 차이가 있나요?

<summary>60. Array와 List 중 어떤 것을 선택해야 하나요?</summary>

반면 일반적인 애플리케이션에서는 크기 조절, 추가/삭제 API, Generic 등을 제공하는 List가 사용하기 편리합니다.

특히 Spring 기반 비즈니스 애플리케이션에서는 대부분 Collection API와 잘 통합되는 List를 사용하는 경우가 많습니다.
