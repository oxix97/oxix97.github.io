API 경로에 명사를 쓰는 것만으로 REST를 설명하기는 어렵다. 리소스와 표현, HTTP의 표준 의미가 어떤 제약 아래 함께 동작하는지 정리한다.

## 핵심 요약

- 리소스는 URI로 식별하고, 표현은 그 리소스의 상태를 메시지에 담아 전달한다.
- REST는 클라이언트·서버 분리, 무상태성, 캐시 가능성, 균일한 인터페이스 등 아키텍처 제약의 조합이다.
- HTTP API는 메서드·상태 코드·표현을 일관되게 사용해 클라이언트와 서버의 결합을 줄인다.
- JSON을 반환하거나 경로에서 동사를 제거했다는 사실만으로 REST 제약을 모두 만족하는 것은 아니다.

## REST는 리소스와 표현을 구분한다

REST는 네트워크 기반 분산 시스템을 위한 아키텍처 스타일이다. 서버 내부 객체를 그대로 공개하는 방식이 아니라 리소스를 식별하고, 메시지의 표현으로 상태를 주고받는다.

`/books/42`는 책 리소스를 식별할 수 있다. 서버는 요청에 따라 JSON이나 다른 표현을 반환한다. URI가 리소스를 가리키고 HTTP 메서드가 처리 의미를 전달하면, 경로를 `getBook`이나 `deleteBook`처럼 동사 중심으로 만들지 않아도 된다.

**URI는 대상을 식별하고, 메서드는 대상에 대한 요청 의미를 전달한다.** 메서드와 멱등성 기준은 [HTTP 요청 글](/study/network/http-methods-status-and-idempotency/)에서 다룬다.

## 균일한 인터페이스가 API 연결을 단순하게 한다

REST의 균일한 인터페이스는 리소스를 식별하고, 표현을 통해 조작하며, 메시지가 자기 설명적이고 하이퍼미디어를 통해 상태 전이가 이어지도록 요구한다. 이 제약이 지켜지면 클라이언트는 특정 서버 구현을 덜 알아도 메시지와 링크로 다음 동작을 찾을 수 있다.

HTTP API에서는 URI, 메서드, 상태 코드, 헤더와 본문이 함께 표현을 이룬다. `GET /books/42`의 성공은 표현을 반환할 수 있고, `POST /books`의 성공은 생성된 리소스의 위치를 `Location`으로 알릴 수 있다. 오류도 상태 코드와 오류 표현으로 전달하면 클라이언트가 결과를 구분하기 쉽다.

HATEOAS는 응답 표현의 링크를 따라 다음 가능한 동작을 발견하게 하는 제약이다. 응답에 `self` 링크만 넣거나 링크가 전혀 없다고 해서 곧바로 모든 API의 사용성이 무너지는 것은 아니지만, 이를 REST의 완전한 균일 인터페이스와 동일시하면 안 된다.

## 다른 제약은 서버와 클라이언트의 책임을 나눈다

클라이언트·서버 구조는 화면과 데이터 저장 책임을 분리한다. 무상태성은 각 요청이 처리에 필요한 정보를 포함하도록 해 서버가 클라이언트 세션에 의존하지 않게 한다. 캐시 가능성은 응답이 재사용 가능한지 명시해 네트워크 요청과 서버 부하를 줄일 수 있게 한다.

계층화 구조에서는 클라이언트가 프록시나 게이트웨이 같은 중간 계층을 거쳐도 된다. Code-on-Demand는 서버가 실행 코드를 전달하는 선택 제약이다. REST의 제약을 모두 같은 방식으로 강제할 필요가 있는지 API의 목적과 운영 환경에서 판단한다.

## 장점과 한계

리소스와 HTTP 의미를 일관되게 사용하면 API 사용자가 경로와 메서드만으로 요청 의도를 이해하기 쉬워진다. 캐시와 중간 계층도 명시된 HTTP 의미를 활용할 수 있다.

REST는 특정 URL 모양이나 JSON 형식을 뜻하지 않는다. 실제 서비스는 하이퍼미디어 제약을 완전히 적용하지 않는 경우가 있어 “RESTful”이라는 이름만으로 클라이언트 결합도나 API 품질을 판단할 수 없다. 필요한 제약과 예외를 문서화해야 한다.

## 기술면접 질문

### REST와 REST API는 무엇인가?

REST는 분산 시스템의 아키텍처 제약을 조합한 스타일이고 REST API는 그 제약을 따르는 인터페이스입니다. 리소스 식별, 표현, 균일한 인터페이스와 무상태성 등이 핵심입니다. 경로가 명사이고 응답이 JSON이라는 사실만으로 REST를 완전히 만족한다고 할 수 없습니다.

### REST API에서 URI와 HTTP 메서드는 어떤 역할을 하는가?

URI는 대상 리소스를 식별하고 HTTP 메서드는 그 대상에 요청하는 동작 의미를 전달합니다. 예를 들어 `GET /books/42`는 책 표현을 조회하고 `DELETE /books/42`는 삭제를 요청합니다. 실제 효과와 응답은 서버의 계약과 상태 코드로 확인해야 합니다.

### REST의 무상태성은 서버가 아무 상태도 저장하지 않는다는 뜻인가?

아닙니다. 무상태성은 요청 사이의 클라이언트 세션 상태에 서버가 의존하지 않는다는 제약입니다. 서버는 리소스 데이터나 업무 상태를 저장할 수 있으며 각 요청은 처리에 필요한 인증과 맥락을 제공해야 합니다.

- [ ] URI와 HTTP 메서드가 요청 의미를 나누는 방식을 설명할 수 있다.
