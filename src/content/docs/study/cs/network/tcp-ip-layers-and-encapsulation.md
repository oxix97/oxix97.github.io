## 핵심 요약

TCP/IP 4계층은 애플리케이션, 전송, 인터넷, 네트워크 접근 계층이 서로 다른 책임을 나누어 데이터를 전달하는 모델이다. HTTP 같은 애플리케이션 데이터는 전송 계층에서 TCP 세그먼트가 되고, 인터넷 계층에서 IP 패킷이 되며, 로컬 링크를 지날 때 프레임으로 전달된다. 수신 측은 이 순서의 반대로 각 헤더를 해석해 상위 계층에 데이터를 넘긴다.

## TCP/IP 4계층의 책임

애플리케이션 계층은 HTTP, HTTPS, SMTP, SSH처럼 애플리케이션이 네트워크 기능을 이용하도록 하는 프로토콜을 제공한다. 전송 계층은 포트로 애플리케이션 서비스를 구분하고 TCP 또는 UDP로 종단 간 전달을 담당한다. TCP는 신뢰성 있는 순서 보장 바이트 스트림을 제공하며, 이를 위해 순서 번호, 확인 응답, 재전송 같은 동작을 사용한다.

인터넷 계층은 IP 주소와 라우팅을 통해 다른 네트워크의 목적지까지 패킷을 전달한다. 네트워크 접근 계층은 현재 연결된 로컬 링크에서 프레임을 만들어 전선, 광섬유, 무선 같은 매체로 보내는 일을 맡는다. 따라서 목적지까지의 경로를 정하는 IP 전달과 바로 다음 링크로 보내는 프레임 전달은 같은 책임이 아니다.

## 계층별 PDU와 대표 프로토콜

| 계층 | 책임 | 대표 프로토콜 | PDU |
| --- | --- | --- | --- |
| 애플리케이션 | 사용자·서비스의 네트워크 메시지 형식과 의미를 정의 | HTTP, HTTPS, SMTP, SSH, DNS | 메시지 |
| 전송 | 포트 기반 다중화와 종단 간 전달을 제공 | TCP, UDP | TCP 세그먼트 / UDP 데이터그램 |
| 인터넷 | IP 주소 기반의 패킷 전달과 라우팅을 담당 | IP, ICMP | IP 패킷(데이터그램) |
| 네트워크 접근 | 로컬 링크에서 프레임을 만들고 물리 매체로 전달 | Ethernet, Wi-Fi | 프레임 |

PDU 이름은 어느 계층의 관점으로 데이터를 부르느냐를 나타낸다. RFC 9293은 애플리케이션 바이트 스트림이 TCP 세그먼트로 네트워크를 지나고, 각 TCP 세그먼트가 IP 데이터그램으로 전송된다고 설명한다. TCP와 UDP는 모두 전송 계층이지만 PDU와 전달 특성이 다르므로, 여기서는 TCP 요청의 흐름을 예시로 사용한다.

## 캡슐화와 역캡슐화

캡슐화는 송신 측에서 상위 계층 데이터를 하위 계층으로 넘기며 각 계층의 제어 정보를 붙이는 과정이다. TCP는 포트, 순서 번호, 체크섬 같은 전송 정보를 세그먼트 헤더에 넣고, IP는 출발지·목적지 IP 주소를 IP 헤더에 넣는다. 링크 계층은 다음 홉으로 전달하기 위한 프레임 헤더와 기술에 따라 트레일러를 추가한다.

역캡슐화는 수신 측에서 프레임, IP 패킷, TCP 세그먼트를 차례로 확인해 해당 헤더를 해석하고 상위 계층으로 페이로드를 전달하는 과정이다. 이때 헤더를 단순히 모두 삭제한다기보다, 각 계층이 자신에게 필요한 정보를 검증·처리한 뒤 상위 계층에 넘긴다고 이해하는 편이 정확하다. 중간 라우터는 보통 링크 프레임을 벗기고 IP 패킷을 다음 링크의 새 프레임에 다시 담으므로, 프레임은 홉마다 바뀔 수 있다.

링크 계층의 CRC와 TCP 체크섬은 모두 오류 검출과 관련되지만 같은 보호 장치가 아니다. Ethernet CRC는 해당 링크의 프레임 검증에 쓰이고, TCP 체크섬은 TCP 헤더와 데이터 및 IP 의사 헤더를 포함해 세그먼트의 전달 오류를 검출한다. 따라서 각각의 적용 계층과 보호 범위를 구분해야 한다.

## OSI 7계층과 어떻게 대응하는가

학습할 때는 TCP/IP의 애플리케이션 계층을 OSI의 애플리케이션·표현·세션 계층과, 네트워크 접근 계층을 OSI의 데이터 링크·물리 계층과 대응시켜 볼 수 있다. 전송 계층은 전송 계층에, 인터넷 계층은 네트워크 계층에 대략 대응한다. 이 대응은 역할을 비교하는 학습용 지도이며, 실제 운영체제·네트워크 스택이 반드시 일대일로 분리되어 구현된다는 뜻은 아니다.

OSI 모델은 역할을 세밀하게 나누어 설명하는 데 유용하고, TCP/IP 모델은 인터넷 프로토콜 묶음의 동작을 설명하는 데 가깝다. 두 모델 중 하나가 다른 하나의 정확한 구현 명세라고 생각하기보다, 어떤 책임과 프로토콜을 설명하려는지에 따라 모델을 선택하면 혼동을 줄일 수 있다.

## HTTP 요청이 네트워크를 통과하는 과정

브라우저가 서버에 `GET /articles` HTTP 메시지를 만든다고 가정하자. 송신 측에서는 `HTTP 메시지 → TCP 세그먼트 → IP 패킷 → 링크 프레임` 순서로 캡슐화된다. TCP는 서버 포트와 전달 제어 정보를, IP는 서버까지 가기 위한 주소 정보를, 링크 계층은 현재 로컬 링크의 전달 정보를 추가한다.

프레임은 스위치나 다음 홉으로 전달되고, 라우터는 수신한 프레임을 처리해 IP 목적지에 따라 다음 경로를 결정한다. 라우터를 지날 때마다 로컬 링크용 프레임은 새로 만들어질 수 있지만, 종단 간 통신을 위한 TCP 세그먼트와 IP 패킷의 관계는 유지된다. 목적지 호스트에서는 `링크 프레임 → IP 패킷 → TCP 세그먼트 → HTTP 메시지`의 역순으로 처리되어 웹 서버 애플리케이션에 요청이 도착한다.

## 장점과 한계

계층화는 HTTP 기능, TCP 전달 제어, IP 라우팅, 링크 전송을 독립적인 책임으로 나누므로 프로토콜을 교체하거나 장애 원인을 좁히는 데 도움을 준다. 예를 들어 HTTP 응답 지연을 볼 때 애플리케이션 처리 시간, TCP 재전송, IP 경로, 링크 오류를 같은 문제로 뭉뚱그리지 않고 관측할 수 있다. 각 계층의 인터페이스가 안정적일수록 하위 링크 기술이 바뀌어도 상위 애플리케이션은 영향을 덜 받는다.

반면 계층 모델은 실제 구현의 모든 경계를 그대로 보여 주지는 않으며, 성능·보안·운영 문제는 여러 계층에 걸쳐 나타날 수 있다. TCP 체크섬이나 링크 CRC가 있다고 해서 모든 손상·공격을 막는 것은 아니고, 암호화·인증·관측·재시도 정책도 별도로 설계해야 한다. 모델은 원인을 분해하는 출발점이지 실제 패킷 캡처와 서비스 지표를 대신하는 결론은 아니다.

## 기술면접 질문

### TCP/IP 4계층을 나누는 이유

TCP/IP 4계층은 애플리케이션 기능, 종단 간 전달, IP 라우팅, 로컬 링크 전송의 책임을 분리하기 위해 나눕니다. 이 분리는 HTTP 오류, TCP 재전송, IP 경로, 링크 문제를 서로 다른 관점에서 진단하게 해 줍니다. 하위 링크 기술이 바뀌더라도 상위 프로토콜의 인터페이스를 유지하기 쉬운 점도 장점입니다.

### 캡슐화와 역캡슐화

캡슐화는 송신 측에서 HTTP 메시지에 TCP 헤더, IP 헤더, 링크 계층 정보를 순서대로 붙여 전달 단위를 만드는 과정입니다. 역캡슐화는 수신 측이 프레임부터 각 계층의 정보를 해석하고 상위 계층으로 페이로드를 넘기는 반대 과정입니다. 중간 라우터에서는 IP 패킷을 다음 링크의 새 프레임에 담을 수 있으므로 프레임 정보는 홉마다 바뀔 수 있습니다.

### OSI 7계층과 TCP/IP 4계층의 차이

OSI 7계층은 통신 역할을 애플리케이션부터 물리 계층까지 더 세분화해 설명하는 참조 모델입니다. TCP/IP 4계층은 인터넷 프로토콜 스택의 애플리케이션, 전송, 인터넷, 네트워크 접근 계층을 중심으로 설명합니다. 두 모델의 계층 대응은 개념을 비교하는 데 유용하지만 실제 구현이 반드시 일대일로 나뉜다는 보장은 아닙니다.
