HTTPS를 “데이터를 암호화한다”로만 설명하면 상대가 진짜 서버인지 확인하는 절차가 빠진다. 대칭키, 공개키, 전자서명과 인증서가 어떤 문제를 해결하는지 구분해 보자.

## 핵심 요약

- 대칭키 암호는 같은 비밀키로 데이터를 빠르게 보호한다.
- 공개키 암호는 공개키와 개인키를 역할에 따라 사용해 키 합의나 서명을 돕는다.
- 인증서는 공개키와 서버 이름을 연결하고, 인증서 체인은 신뢰할 수 있는 발급자까지 관계를 이어 준다.
- TLS는 키 합의와 서버 인증을 거친 뒤 대칭키 기반 트래픽 보호를 사용한다.

## 대칭키는 실제 데이터 보호를 맡는다

대칭키 암호는 양쪽이 같은 비밀키를 사용해 데이터를 암호화하고 복호화한다. 공개키 방식보다 대량 데이터를 효율적으로 처리할 수 있지만 통신 전에 양쪽이 비밀키를 안전하게 공유해야 한다.

TLS는 핸드셰이크가 만든 트래픽 키로 애플리케이션 데이터를 보호한다. 현대 TLS에서는 암호화와 무결성 검증을 결합한 AEAD 알고리즘을 사용한다. HTTPS는 TLS를 HTTP 아래에서 사용해 네트워크 구간의 기밀성과 무결성을 제공한다.

## 공개키와 전자서명은 키 합의와 신원 검증을 돕는다

공개키와 개인키는 수학적으로 연결된 한 쌍이다. 키 합의에서는 양쪽이 교환한 공개값으로 같은 공유 비밀을 계산하고, 전자서명에서는 개인키로 서명한 값을 공개키로 검증한다. 용도에 따라 사용하는 방식이 다르다.

TLS 1.3의 일반적인 핸드셰이크는 ECDHE로 세션 비밀을 합의하고, 서버 인증서의 공개키에 대응하는 개인키로 핸드셰이크 내용을 서명한다. 인증서 개인키를 애플리케이션 데이터 암호화에 직접 쓰는 구조가 아니다.

## 인증서는 공개키를 서버 이름에 연결한다

인증서는 인증 기관이 서명한 공개키와 신원 정보의 묶음이다. 브라우저는 인증서 체인을 신뢰 앵커까지 확인하고, 접속한 호스트 이름이 인증서의 이름과 일치하는지 검사한다. 인증 기관 서명이 맞더라도 이름이 다르거나 기간이 만료되면 해당 서버 인증은 실패할 수 있다.

**인증서 확인은 암호화된 키를 만드는 과정과 별개로, 공개키가 접속하려는 서버의 것인지 확인한다.** 이 검증을 통과한 뒤 TLS 핸드셰이크에서 키 합의와 트래픽 키 설정이 이어진다. 상세 흐름은 [TLS 1.3 핸드셰이크 글](/study/network/https-tls-1-3-handshake/)에서 다룬다.

## 장점과 한계

역할을 나누면 공개키 방식으로 서버를 인증하고 세션 키를 합의한 뒤 대칭키로 데이터를 효율적으로 보호할 수 있다. 인증서 체인은 각 클라이언트가 처음부터 모든 서버 공개키를 보관하지 않아도 신뢰 관계를 확인하게 해 준다.

HTTPS는 서버 애플리케이션이 정직하거나 안전하다는 보증은 아니다. 인증 기관과 신뢰 저장소, 이름 검증이 올바르게 동작해야 하며 피싱 사이트도 자기 도메인에 유효한 인증서를 얻을 수 있다.

## 기술면접 질문

### TLS가 대칭키와 공개키 방식을 함께 쓰는 이유는 무엇인가?

공개키 방식은 서버 인증과 키 합의를 돕고 대칭키는 실제 데이터를 효율적으로 보호합니다. 공개키 방식만으로 모든 트래픽을 처리하지 않아도 되므로 역할과 비용을 나눌 수 있습니다. TLS 1.3의 구체적인 키 설정 순서는 핸드셰이크에서 확인합니다.

### 인증서가 서버를 인증하는 방식은 무엇인가?

인증서는 인증 기관이 공개키와 신원 정보를 연결해 서명한 자료입니다. 클라이언트는 신뢰 체인과 유효 기간, 접속한 서버 이름을 확인하고 서버는 대응하는 개인키의 소유를 증명합니다. 인증서에 서명이 있다는 사실만으로 이름 검증을 생략할 수는 없습니다.

### HTTPS를 사용하면 사이트 자체도 안전하다고 볼 수 있는가?

그렇지 않습니다. HTTPS는 클라이언트와 인증된 호스트 사이의 전송을 보호합니다. 악성 콘텐츠, 취약한 애플리케이션, 피싱 도메인처럼 전송 암호화만으로 해결되지 않는 문제는 별도로 판단해야 합니다.
