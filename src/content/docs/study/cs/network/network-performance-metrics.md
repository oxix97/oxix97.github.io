대역폭이 충분해 보이는데도 API가 느린 상황은 흔하다. 이때 용량, 실제 전송률, 왕복 지연을 같은 숫자처럼 다루면 증설과 코드 개선 중 무엇이 필요한지 판단하기 어렵다.

## 핵심 요약

- 대역폭은 링크의 용량 상한이고, 처리량은 정한 계층과 구간에서 실제로 달성한 전송률이다.
- 트래픽은 관측 지점을 지난 부하를 뜻한다. 처리량과 비교하려면 단위·시간 창·계층을 먼저 맞춰야 한다.
- RTT는 두 방향 경로를 합친 왕복 지연이다. API 응답 시간은 RTT에 연결 설정, 서버 처리, 데이터 전송 등이 더해진 별도 지표다.

같은 `Mbps` 단위를 써도 무엇을 세었는지에 따라 값의 의미가 달라진다. 다음 질문으로 측정 범위를 먼저 고정한다.

| 용어 | 이 글에서의 뜻 | 혼동을 막는 확인 질문 |
| --- | --- | --- |
| 트래픽 | 관측 지점을 일정 시간 동안 지난 데이터의 양 또는 전송률 | 어느 인터페이스·방향·계층의 바이트를 세었는가? |
| 처리량 | 정한 구간에서 실제로 달성한 전송률 | 헤더와 재전송까지 포함했는가, 애플리케이션 데이터만 세었는가? |
| 대역폭 | 링크가 단위 시간에 전달하도록 설계된 용량의 상한 | 개별 링크 용량인가, 경로의 병목 대역폭인가? |
| RTT | 송신한 측이 대응 응답을 받을 때까지의 왕복 지연 | 어떤 프로브와 응답 지점을 사용했고 상대 처리 시간이 얼마나 섞였는가? |

## 트래픽과 처리량의 차이

트래픽은 하나의 표준화된 단일 지표 이름이라기보다 관측된 부하를 가리키는 운영 용어에 가깝다. NIC의 송신 바이트, 라우터 인터페이스의 비트율, HTTP 응답 본문 크기는 모두 트래픽으로 부를 수 있지만 측정 계층이 다르다. 따라서 값에는 관측 위치, 방향, 시간 구간, 단위를 함께 기록해야 한다.

처리량도 계층을 명시해야 한다. 링크 처리량에는 프레임 헤더와 재전송이 포함될 수 있지만, 애플리케이션이 받은 유효 데이터만 센 값은 보통 유효 처리량(goodput)으로 구분한다. 패킷 손실로 재전송이 늘면 링크 사용량은 커져도 유효 처리량은 떨어질 수 있다.

**트래픽과 처리량을 비교할 때는 같은 관측 지점·시간 창·계층의 값인지 먼저 확인한다.**

예를 들어 목록 API의 호출 수와 응답 크기가 함께 늘면 송신 트래픽이 증가한다. 이때 NIC 전송률은 높은데 클라이언트가 받은 본문 기준 유효 처리량이 낮다면 재전송이나 응답 지연을 추가로 살핀다. Kafka 생산 레코드 수와 소비 완료 레코드 수도 서로 다른 처리 단계의 값이므로 네트워크 처리량과 한 그래프에서 같은 의미로 비교하면 안 된다.

## 대역폭과 실제 처리량이 다른 이유

링크 대역폭은 용량의 상한일 뿐, 애플리케이션이 그대로 사용할 수 있는 비트율은 아니다. 여러 흐름이 용량을 나누고 각 계층의 헤더가 일부를 차지한다. 경로의 혼잡, 패킷 손실과 재전송, 송수신 호스트의 처리 능력도 실제 처리량을 제한한다.

TCP에서는 수신 윈도, 혼잡 윈도, RTT도 한 연결이 채울 수 있는 전송량에 영향을 준다. 대역폭-지연 곱(BDP)은 경로를 충분히 활용하려면 전송 중에 유지해야 할 데이터 양을 가늠하게 한다. 링크가 빨라도 윈도가 BDP보다 작거나 손실로 혼잡 윈도가 줄면 한 TCP 연결의 처리량은 대역폭에 미치지 못한다.

gRPC 스트리밍은 연결을 재사용하고 메시지마다 별도 요청·응답을 기다리는 흐름을 줄일 수 있다. 그러나 HTTP/2와 gRPC의 흐름 제어, 수신 서비스의 역압력, 중간 경로의 혼잡이 있으면 기대 처리량이 나오지 않는다. 외부 API도 호출 측 링크뿐 아니라 상대의 처리 한도와 경로 정책에 영향을 받는다.

## RTT가 API 응답 시간에 미치는 영향

RTT는 한 종단에서 보낸 프로브에 대응하는 응답이 돌아올 때까지의 시간이다. 전방과 역방향 경로가 다를 수 있으므로 두 방향의 상태가 한 값에 섞인다. ICMP Echo, TCP 데이터와 ACK처럼 측정 방식도 다르며, 응답 종단의 처리 시간은 측정 오차나 불확실성으로 포함될 수 있다.

관측 구간으로 나누면 동기 API 응답 시간은 연결 설정 시간, 요청 후 첫 응답 바이트까지의 시간(TTFB), 이후 본문 전송 시간으로 볼 수 있다. TTFB 안에는 요청 전송, 서버·데이터베이스 처리, 첫 바이트가 돌아오는 시간이 함께 들어간다. 기존 연결을 재사용하는지, TLS를 새로 협상하는지, 응답 크기가 얼마인지에 따라 필요한 왕복과 전송 시간이 달라진다. 따라서 ping RTT를 API 응답 시간에서 단순히 빼서 서버 처리 시간을 구할 수는 없다.

**애플리케이션 처리 시간과 네트워크 왕복 시간을 분리**하되, RTT를 API 응답 시간과 같은 값으로 보지 않는다.

분산 추적으로 서버 구간과 의존성 대기를 보고, TCP·호스트 지표로 재전송과 RTT 변화를 함께 본다. RTT가 안정적인데 서버 span이 길어졌다면 애플리케이션이나 의존성을 우선 조사한다. 반대로 같은 시점에 RTT와 재전송이 증가했다면 경로 혼잡이나 손실을 가설로 둔다. 비동기 흐름은 사용자 응답 시간과 메시지 발행·소비 완료 지연을 별도 지표로 둔다.

API 응답 시간이 증가하면 다음 순서로 확인한다.

1. 요청과 응답의 데이터 크기가 변했는지 확인해 전송해야 할 양 자체가 커졌는지 본다.
2. 같은 계층과 시간 창의 대역폭·처리량·유효 처리량을 비교한다.
3. RTT, 재전송, 손실, 인터페이스 포화를 함께 보고 경로 문제의 근거를 찾는다.
4. 연결·TLS 설정, 서버 처리, 데이터베이스·외부 의존성 대기를 trace로 분리한다.

## 장점과 한계

트래픽·처리량·대역폭·RTT를 구분하면 병목을 찾기 위한 질문을 순서대로 세울 수 있다. 네트워크 용량 증설, TCP 설정 점검, 쿼리 개선, 호출 방식 변경 중 무엇을 먼저 검토할지 근거도 선명해진다.

그러나 측정 지점과 시간 구간이 다르면 같은 이름의 지표도 직접 비교할 수 없다. RTT는 두 방향을 합친 값이라 어느 방향이 느린지도 알려 주지 않는다. 캐시, 큐 적체, 상대 서비스의 제한은 별도 관측이 필요하므로 지표 하나를 원인으로 단정하지 않는다.

## 기술면접 질문

### 대역폭과 처리량의 차이

대역폭은 링크가 단위 시간에 전달하도록 설계된 용량의 상한이고, 처리량은 정한 구간과 계층에서 실제로 달성한 전송률입니다. 프로토콜 오버헤드, 경로 혼잡, 손실, TCP 윈도, 종단 처리 능력 때문에 처리량은 대역폭보다 낮을 수 있습니다. 애플리케이션 유효 데이터만 세려면 유효 처리량의 측정 범위도 따로 명시해야 합니다.

### RTT가 API 응답 시간에 주는 영향

RTT는 한 종단이 프로브를 보낸 뒤 대응 응답을 받을 때까지의 왕복 지연입니다. 측정 방식에 따라 두 방향 경로뿐 아니라 응답 종단의 처리 불확실성도 포함될 수 있습니다. API 응답 시간에는 연결과 TLS 설정, 서버·의존성 처리, 데이터 전송이 더해지므로 RTT와 같은 값으로 해석하면 안 됩니다.

### 네트워크 병목과 애플리케이션 지연을 구분하는 방법

먼저 요청 경로와 측정 지점을 정하고 같은 시간 창의 트래픽, 처리량, 오류, 포화를 비교합니다. 그다음 RTT·재전송과 분산 추적의 서버·의존성 시간을 나누어 봅니다. RTT와 재전송이 증가하면 경로를, 서버 span이나 큐 대기가 증가하면 해당 애플리케이션 구간을 우선 조사합니다.

## 복습 체크리스트

- [ ] 트래픽 지표에 관측 위치·방향·시간 창·계층이 필요한 이유를 설명할 수 있다.
- [ ] 트래픽을 링크를 오가는 데이터 흐름의 양으로, 처리량을 성공 전달 결과로 구분해 설명할 수 있다.
- [ ] 대역폭이 최대 용량이지 실제 처리량 자체가 아니라는 점을 설명할 수 있다.
- [ ] 처리량과 애플리케이션 유효 처리량의 측정 범위를 구분할 수 있다.
- [ ] RTT를 API 응답 시간과 같은 값으로 보지 않고 측정 방식의 불확실성을 설명할 수 있다.
- [ ] RTT와 애플리케이션 처리 시간을 분리해 API 지연 원인을 확인할 수 있다.
- [ ] RTT·재전송과 trace의 서버·의존성 시간을 함께 비교할 수 있다.
- [ ] REST API, gRPC, Kafka, 외부 API가 각각 어떤 관측 맥락을 만드는지 구분할 수 있다.
