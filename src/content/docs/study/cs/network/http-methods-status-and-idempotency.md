주문 API의 응답을 받기 전에 연결이 끊기면 같은 요청을 다시 보내도 될까? 이 질문에 답하려면 HTTP 메서드가 표현하는 의도와 서버가 실제로 보장하는 중복 방지를 나눠 봐야 한다. [HTTP/1 글](/study/network/http-messages-and-http-1/)과 [HTTP/2·3 글](/study/network/http-2-and-http-3/)이 메시지 전달 방식을 다뤘다면, 여기서는 메시지의 의미를 살핀다.

## 핵심 요약

- 메서드는 대상 리소스에 대해 클라이언트가 요청하는 동작을 나타내고, 상태 코드는 처리 결과를 나타낸다.
- GET은 조회, POST는 대상 리소스별 처리, PUT은 대상 리소스 상태의 교체를 요청한다. PATCH는 패치 문서의 규칙에 따라 변경을 적용한다.
- 동일한 멱등 요청을 여러 번 보냈을 때 의도된 서버 상태는 한 번 보낸 결과와 같다. 응답 코드까지 같아야 한다는 뜻은 아니다.
- 주문 생성 같은 POST를 안전하게 재시도하려면 업무 수준의 중복 방지와 결과 조회 방법을 별도로 설계한다.

## 메서드와 상태 코드는 서로 다른 질문에 답한다

`GET /orders/42`는 주문의 현재 표현을 요청한다. `POST /orders`는 주문 목록 리소스가 요청 본문을 처리하도록 요청한다. 서버가 새 주문을 만들었다면 `201 Created`와 새 리소스의 `Location`을 반환할 수 있다. 검증 실패에는 4xx, 처리 중 서버 오류에는 5xx를 쓸 수 있지만, 코드는 실제 결과에 맞게 골라야 한다.

| 상태 코드 묶음 | 뜻 | 주문 API에서 확인할 점 |
| --- | --- | --- |
| 2xx | 요청을 성공적으로 처리했다 | 생성이라면 201, 본문 없는 성공이라면 204 등 결과에 맞는가 |
| 3xx | 다른 위치 또는 조건에 따른 후속 동작이 필요하다 | 클라이언트가 따라갈 위치와 캐시 규칙은 무엇인가 |
| 4xx | 요청을 처리할 수 없거나 허용하지 않는다 | 입력, 인증, 권한, 대상 리소스 중 무엇이 문제인가 |
| 5xx | 서버가 요청 처리에 실패했다 | 재시도 전에 처리 여부를 확인할 방법이 있는가 |

**상태 코드만으로 앞선 요청의 업무 효과가 없었다고 단정하지 않는다.** 클라이언트가 타임아웃을 봤더라도 서버는 주문을 저장한 뒤 응답 전달에 실패했을 수 있다.

## GET·POST·PUT·PATCH의 선택 기준

| 메서드 | 요청의 의도 | 기본 멱등성 판단 |
| --- | --- | --- |
| GET | 대상 리소스의 표현을 가져온다 | 안전하고 멱등하다. 조회가 주문을 생성해서는 안 된다. |
| POST | 대상 리소스가 본문을 자체 규칙으로 처리한다 | 일반적으로 멱등하지 않다. 주문 생성이 대표적이다. |
| PUT | 지정한 대상 리소스의 상태를 표현으로 교체한다 | 같은 표현을 반복 적용하는 의도는 멱등하다. |
| PATCH | 패치 문서의 지시에 따라 일부를 변경한다 | 형식과 연산에 달려 있다. 무조건 멱등하다고 볼 수 없다. |

`PUT /profiles/42`에 동일한 프로필 표현을 반복 보내는 경우와 `PATCH /counters/42`에 `1 증가`를 반복 적용하는 경우를 비교해 보자. 앞의 요청은 같은 상태를 목표로 하지만, 뒤의 요청은 반복 횟수만큼 값이 달라진다. PATCH도 `상태를 active로 설정`처럼 멱등하게 설계할 수 있다.

GET이 URL에만 데이터를 넣고 POST가 본문에만 데이터를 넣는다는 구분은 메서드의 정의가 아니다. URL 길이를 특정 숫자로 고정하는 규칙도 HTTP 메서드 의미에는 없다. 민감한 값은 메서드 이름만 믿지 말고 HTTPS, 로그, URL 노출, 접근 제어를 함께 검토한다.

## 주문 요청을 재시도해야 한다면

```text
클라이언트: POST /orders, Idempotency-Key: 요청별 고유값
서버: 키와 요청 내용 확인 → 주문 생성 → 키와 결과를 원자적으로 기록
응답이 유실됨
클라이언트: 같은 키와 같은 요청으로 재시도
서버: 기록된 결과를 조회해 중복 주문을 만들지 않음
```

이 흐름은 HTTP가 POST에 자동으로 제공하는 보장이 아니라 애플리케이션 설계 예시다. 키의 유효 기간, 같은 키에 다른 본문이 왔을 때의 거절 방식, 동시 요청의 원자성, 최종 DB 제약 조건까지 정해야 한다. 결제처럼 외부 시스템이 끼면 그 시스템의 중복 처리 계약도 확인해야 한다.

REST도 단순히 URL에 명사를 쓰는 규칙으로 끝나지 않는다. [REST API 글](/study/network/rest-api/)에서 정리한 리소스 식별과 제약 조건을 함께 보고, 표준 메서드의 의미와 응답 표현을 일관되게 사용하면 클라이언트와 중간 장치가 요청을 이해하기 쉬워진다. 특정 API가 REST라고 불리는지보다 **재시도와 캐시가 메서드의 의미를 어기지 않는지** 먼저 확인한다.

## 장점과 한계

메서드와 상태 코드를 일관되게 쓰면 클라이언트가 성공, 오류, 재시도를 판단하기 쉽다. 멱등 요청은 응답 유실 뒤 반복할 때 의도된 상태가 흔들리지 않도록 돕는다.

다만 멱등성은 모든 부수 효과가 한 번만 일어난다는 약속이 아니다. 요청 로그나 이력은 반복마다 남을 수 있다. POST의 중복 방지는 HTTP 문법이 아니라 서버의 저장·동시성 설계로 검증해야 한다.

## 기술면접 질문

### PUT과 PATCH는 어떻게 다른가?

PUT은 지정한 리소스의 상태를 요청 표현으로 교체하려는 메서드입니다. PATCH는 패치 문서의 지시에 따라 변경을 적용합니다. PUT의 의도는 멱등하지만 PATCH는 연산에 따라 멱등할 수도, 아닐 수도 있습니다.

### 같은 PUT을 두 번 보내면 응답도 같아야 하는가?

그렇지 않습니다. 멱등성은 동일 요청을 반복했을 때 의도된 서버 상태에 관한 성질입니다. 처음에는 생성되어 201, 다음에는 갱신되어 200이나 204를 반환하는 등 응답은 달라질 수 있습니다.

### 주문 생성 POST의 응답이 유실되면 어떻게 재시도하는가?

먼저 서버가 주문을 이미 처리했을 가능성을 고려해야 합니다. 요청별 중복 방지 키를 사용하고 처리 결과를 조회할 수 있게 합니다. 키와 결과를 원자적으로 기록하고 DB 제약도 두어 같은 업무 요청의 재전송이 중복 주문을 만들지 않게 합니다.

## 복습 체크리스트

- [ ] GET·POST·PUT·PATCH를 대상 리소스에 대한 의도로 설명할 수 있다.
- [ ] 응답 상태 코드와 서버의 실제 업무 처리 여부를 구분할 수 있다.
- [ ] 멱등성이 동일 응답이나 부수 효과 제로를 뜻하지 않음을 설명할 수 있다.
- [ ] 주문 POST의 응답이 유실됐을 때 중복 방지 흐름을 설계할 수 있다.
