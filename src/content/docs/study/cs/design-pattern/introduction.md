카드 결제만 되던 쇼핑몰에 계좌 이체를 추가한다고 해 보자. 결제 코드 한 곳만 바꾸면 될까, 주문을 처리하는 여러 곳을 함께 고쳐야 할까? 디자인 패턴은 이런 변경을 어디에서 감당할지 정하는 데 도움을 준다.

이 연재는 결제·주문·알림처럼 익숙한 상황에서 출발한다. 먼저 그림으로 역할과 흐름을 살펴보고, Java 예제에서 그 역할을 찾는 순서로 읽으면 된다.

## 핵심 요약

디자인 패턴은 반복해서 나타나는 설계 문제를 해결하는 방법에 붙인 이름이다. 완성된 코드를 그대로 가져오는 것이 아니라, 누가 어떤 일을 맡고 서로 어떻게 연결할지를 참고한다.

핵심은 **코드 재사용 자체보다 변경 지점을 격리하고, 팀이 같은 이름으로 설계를 논의하게 하는 데** 있다. 결제 방법이 늘어날 때 주문 처리 전체를 고치는 대신, 결제 부분을 중심으로 고칠 수 있게 만드는 식이다.

패턴을 적용하면 역할과 연결이 늘어난다. 바뀔 일이 거의 없는 작은 기능은 단순한 함수와 조건문으로 두어도 된다.

## 디자인 패턴이 해결하는 문제

주문 코드는 주문 금액을 계산하고 결제를 요청한다. 여기에 카드 승인 절차까지 직접 넣으면, 카드 회사의 호출 방식이 바뀔 때 주문 코드도 수정해야 한다. 계좌 이체를 추가할 때도 주문 흐름 안에 새로운 분기를 넣게 된다. 문제는 조건문 자체가 아니라 **함께 바뀔 이유가 없는 코드가 묶인 것**이다.

아래 그림은 결제 수단을 추가할 때 바뀌는 부분을 비교한다. 화살표는 일을 요청하는 방향이고, ‘수정’과 ‘추가’ 표시는 작업이 필요한 위치다. 실제 결제에서는 두 구현 중 선택한 하나를 사용한다.

여기서 객체는 데이터와 그 데이터를 다루는 기능을 묶은 프로그램의 구성 요소다. 인터페이스는 객체를 사용하는 쪽과 제공하는 쪽이 지킬 기능의 약속이다. 주문 객체가 결제 객체의 기능을 사용하면 주문이 결제에 ‘의존한다’고 말한다.

디자인 패턴은 이런 상황에서 일을 나누는 방법을 제안한다. 전략 패턴은 주문 흐름에서 실제 결제 방식을 분리해 교체할 수 있게 한다. 뒤에서 다룰 옵저버 패턴은 주문 뒤에 이어지는 알림 같은 작업을 분리한다. 이름을 외우기 전에 다음 세 질문을 먼저 확인한다.

- 무엇이 자주 바뀌는가?
- 그 변경을 누가 알아야 하는가?
- 변경에 따라 함께 수정되는 코드는 어디까지인가?

패턴은 복잡한 코드를 꾸미는 장식이 아니라 변경 비용을 조절하는 선택이다. 변화가 거의 없는 작은 기능에는 단순한 함수와 조건문이 낫다.

## 패턴은 코드가 아니라 설계 언어다

패턴 적용은 클래스 이름을 `Strategy`로 바꾸는 일이 아니다. 문제의 맥락과 역할, 의존 방향, 선택의 결과를 함께 설명할 수 있어야 한다. 교체할 정책이 하나뿐이고 변화 가능성도 낮다면 전략 패턴은 과한 추상화가 된다.

이름이 주는 가장 큰 이점은 협업이다. "배송비 계산은 전략으로 분리하자"라고 말하면 팀은 대체 가능한 정책과 호출 지점을 빠르게 합의한다. 이러한 공통 명칭은 코드 밖에서도 설계 의도를 빠르게 공유하게 한다.

이름이 사고를 대신해서는 안 된다. 왜 그 경계를 택했는지와 새 요구에서 어디가 바뀌는지를 설명해야 한다. 면접에서도 정의 암기보다 이 판단을 사례로 말하는 편이 낫다.

## 생성·구조·행동 패턴

디자인 패턴이 GoF에 한정되지는 않지만, 객체지향 설계 문제를 탐색하는 색인으로 생성·구조·행동 분류가 유용하다.

| 분류 | 중심 질문 | 대표 예시 | 살펴볼 변화 |
| --- | --- | --- | --- |
| 생성 | 객체를 누가, 어떻게 만들 것인가? | 싱글톤, 팩토리 메서드, 추상 팩토리, 빌더 | 생성 절차·구체 타입 |
| 구조 | 객체와 클래스를 어떻게 조합할 것인가? | 어댑터, 프록시, 데코레이터 | 연결 방식·책임 배치 |
| 행동 | 객체가 어떻게 협력하고 책임을 나눌 것인가? | 전략, 옵저버, 이터레이터 | 알고리즘·상태 변화·통신 방식 |

여기서 팩토리는 객체 생성을 별도 책임으로 분리하는 접근을 통칭하며, GoF 패턴에는 팩토리 메서드와 추상 팩토리가 포함된다. 생성 패턴은 생성 절차와 구체 타입을 감추고 싶을 때, 구조 패턴은 접근 제어·호환·부가 기능을 붙일 때, 행동 패턴은 알고리즘·상태 변화·객체 간 통신 책임을 나눌 때 살핀다. 한 문제에 여러 분류가 함께 쓰일 수 있다.

## 라이브러리와 프레임워크

라이브러리와 프레임워크는 모두 미리 만들어 둔 기능을 제공한다. 차이를 볼 때는 ‘누가 호출을 시작하는가’를 살펴보면 된다. API는 다른 코드가 제공하는 기능을 사용할 수 있는 접점이다.

라이브러리는 내가 작성한 코드가 필요한 순간 호출한다. 프레임워크는 요청 처리 같은 큰 흐름을 맡고, 약속된 시점에 내가 작성한 코드를 호출한다. 그림에서 호출 화살표의 출발점에 주목하자.

</figure>

이처럼 실행 흐름의 주도권이 프레임워크로 넘어가는 관계를 제어의 역전(Inversion of Control, IoC)이라고 부른다. 프레임워크는 언제 코드를 실행할지 정하고, 개발자는 그때 실행할 동작을 작성한다.

| 구분 | 호출 주체 | 구조 제약 | 교체 범위 |
| --- | --- | --- | --- |
| 라이브러리 | 애플리케이션이 필요할 때 라이브러리 API를 호출한다. | 파일 배치와 실행 흐름을 대체로 애플리케이션이 결정한다. | 호출부가 국소화돼 있다면 같은 목적의 다른 라이브러리로 상대적으로 교체하기 쉽다. |
| 프레임워크 | 프레임워크가 생명주기와 규칙에 따라 애플리케이션 코드를 호출한다. | 프로젝트 구조, 설정 방식, 확장 지점에 일정한 규칙이 있다. | 핵심 흐름과 맞물려 있어 교체는 아키텍처 수준의 비용을 동반할 수 있다. |

HTTP 요청 도구는 애플리케이션이 호출 시점과 흐름을 정하므로 라이브러리에 가깝다. 웹 프레임워크는 라우팅·요청 처리 같은 큰 흐름을 제공하고, 개발자는 약속된 지점에 코드를 넣는다. 실제 도구는 두 성격을 함께 가질 수 있다. 따라서 이름보다 특정 실행 흐름의 제어권을 누가 가지는지로 판단한다. 이 구분은 이후 DI·DIP와 MVC에서 프레임워크가 객체 생성과 실행 흐름을 어떻게 주도하는지 이해하는 기반이 된다.

## 언제 패턴을 적용할 것인가

먼저 단순하게 구현하고, 다음처럼 변화가 반복되거나 구체적으로 예상될 때 패턴을 검토한다. 예를 들어 새 결제 수단이 추가될 때 주문 서비스와 여러 분기문이 함께 바뀌는지, 결제 정책 구현만 추가하면 되는지를 확인한다.

- 같은 분기문이나 생성 코드가 여러 곳에서 함께 바뀐다.
- 외부 시스템이나 정책을 바꾸기 어려워 테스트가 막힌다.
- 이벤트 후속 작업이 늘어 원래 책임이 비대해진다.
- 같은 설계 문제를 반복 설명하느라 의사결정이 느려진다.

한 번만 쓰는 기능, 변할 근거가 없는 규칙, 팀이 유지할 수 없는 계층에는 패턴을 보류한다.

## 장점과 한계

설계 구조를 나누면 변경 지점과 역할이 드러나고, 새 구현 추가와 대체 구현 주입이 쉬워진다.

한계도 분명하다. 인터페이스와 객체 수가 늘면 작은 흐름도 따라가기 어렵고, 요구보다 앞선 추상화는 변경 비용을 키운다. 패턴을 제거했을 때 잃는 것을 설명할 수 있어야 한다.

## 기술면접 질문

### 디자인 패턴을 사용하는 이유

반복되는 설계 문제에서 변경 지점을 격리하고, 팀이 같은 용어로 구조를 논의하기 위해 사용합니다. 예를 들어 결제 수단별 분기를 전략으로 분리하면 새 결제 정책이 추가돼도 주문 서비스의 변경 범위를 줄일 수 있습니다. 교체 가능성이 낮은 코드까지 추상화하면 복잡도만 늘어나므로 변화 가능성과 반복 여부를 보고 적용합니다.

### 라이브러리와 프레임워크의 차이

핵심 차이는 제어 흐름의 주도권입니다. 라이브러리는 애플리케이션이 필요한 시점에 호출하지만, 프레임워크는 정해진 생명주기와 확장 지점에서 애플리케이션 코드를 호출합니다. 프레임워크는 일관된 구조를 제공하는 대신 구조적 결합과 교체 비용이 더 커질 수 있습니다.

### 패턴을 항상 적용하면 안 되는 이유

패턴은 비용이 있는 선택입니다. 변화가 없는 작은 기능에 적용하면 인터페이스, 객체, 간접 호출이 늘어 읽기와 디버깅 비용이 이점보다 커질 수 있습니다. 반복되거나 구체적으로 예상되는 변경이 있을 때 적용하는 것이 적절합니다.

## 복습 체크리스트

- [ ] 디자인 패턴을 코드 템플릿이 아니라 문제·맥락·역할의 조합으로 설명할 수 있다.
- [ ] 생성·구조·행동 패턴이 각각 어떤 질문에서 시작하는지 구분할 수 있다.
- [ ] 라이브러리와 프레임워크의 차이를 호출 주체와 제어의 역전으로 설명할 수 있다.
- [ ] 패턴 적용 전에 변화 가능성과 복잡도 비용을 점검할 수 있다.
