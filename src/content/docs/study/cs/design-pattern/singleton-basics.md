주문 기능과 알림 기능이 같은 애플리케이션 설정을 읽는다고 해 보자. 각 기능이 설정 객체를 따로 만들 수도 있고, 하나를 함께 사용할 수도 있다. 싱글톤은 하나의 객체를 만들어 공유하는 방법이며, 이 글에서는 그 구조와 공유하면 안 되는 상태를 함께 살펴본다.

## 핵심 요약

싱글톤 패턴은 특정 클래스의 인스턴스를 하나만 만들고 여러 호출자가 공유하게 하는 생성 패턴이다. 클래스가 객체의 설계도라면, 인스턴스는 그 설계도로 실제 만들어진 객체다. 여러 곳에서 사용해도 같은 객체를 받는다는 점이 핵심이다.

만드는 비용이 큰 객체를 반복해서 생성하지 않아도 된다는 이점이 있다. 다만 여러 곳이 함께 쓰는 값을 바꾸면 다른 기능과 테스트에도 영향을 줄 수 있다.

따라서 "하나면 충분한가"보다 **이 객체의 생성·공유·변경이 다른 모듈에 어떤 영향을 주는가**를 먼저 확인해야 한다. 다음 글에서는 이 기본 구조가 동시 호출에서도 하나만 생성되도록 만드는 구현 방식을 비교한다.

## 싱글톤이 해결하려는 문제

애플리케이션 설정을 읽어 `AppSettings` 객체에 담는다고 해 보자. 주문 기능과 알림 기능에서 각각 설정을 읽고 객체를 만들면 같은 초기화 작업을 반복한다. 설정이 모든 기능에 공통이고 읽기 전용이라면, 한 번 초기화한 객체를 함께 쓰는 방법을 고려할 수 있다.

중요한 것은 ‘모든 객체를 하나로 줄인다’가 아니라 ‘공유해도 되는 객체를 한 번 만들고 재사용한다’는 점이다. 사용자마다 내용이 달라야 하는 장바구니에는 이 판단을 그대로 적용할 수 없다.

데이터베이스 연결도 생성과 해제에 I/O, 즉 외부와 데이터를 주고받는 비용이 든다. 실제 서비스는 보통 여러 연결을 재사용하는 커넥션 풀을 둔다. 풀 관리 객체를 공유하는 것과 개별 연결을 하나만 두는 것은 다르다. 싱글톤은 공유 객체의 수명과 접근점을 정하는 선택이지, 모든 비싼 자원의 개수를 하나로 제한하는 규칙이 아니다.

## 하나의 인스턴스를 보장하는 구조

먼저 ‘누가 만들어서 누구에게 돌려주는가’를 보자. 외부 코드는 설정 객체를 직접 만들지 않고 `getInstance()`에 요청한다. 이 메서드는 클래스 내부에 보관한 같은 객체를 돌려준다.

Java에서는 생성자를 `private`으로 감춰 외부의 `new`를 막는다. `new`는 새 객체를 만드는 표현이고, 생성자는 그 객체를 초기화할 때 실행되는 코드다. `private`은 여기서 클래스 밖에서 생성자를 부를 수 없다는 뜻이다.

공유할 객체는 `static` 필드에 보관한다. `static` 필드는 객체마다 따로 생기는 값이 아니라 클래스에 속하는 값이다. 다음 예시에서는 이 필드에 객체 하나를 담고 정적 접근 메서드로 돌려준다. 여러 스레드가 동시에 처음 접근할 때의 초기화 방식은 다음 글에서 비교한다.

## Java로 보는 최소 예시

아래 코드에서는 세 곳을 보면 된다. `INSTANCE`는 공유 객체를 보관하고, `private AppSettings()`는 외부 생성을 막으며, `getInstance()`는 보관한 객체를 돌려준다.

```java
public final class AppSettings {
    private static final AppSettings INSTANCE = new AppSettings();

    private AppSettings() {
    }

    public static AppSettings getInstance() {
        return INSTANCE;
    }
}
```

`new AppSettings()`는 클래스 내부에서 한 번만 실행된다. 외부 코드는 `AppSettings.getInstance()`로만 인스턴스에 접근하므로, `AppSettings`를 사용하는 곳은 모두 같은 객체를 참조한다.

## 어디에 사용할 수 있는가

공유해도 안전하고, 생성 또는 초기화 비용을 줄일 근거가 있는 객체에 후보가 된다. 예를 들어 애플리케이션 전역 설정을 읽기 전용으로 제공하는 객체나, 하나의 커넥션 풀을 관리하는 객체를 검토할 수 있다.

설정 초기화 결과를 여러 곳에서 공유하고 캐시해야 한다고 가정해 보자. 싱글톤을 쓰면 인스턴스 생성은 `AppSettings`에 모이고 호출부는 같은 접근점을 사용한다. 다만 의존성 주입도 정적 전역 접근 없이 객체의 수명을 한곳에서 관리할 수 있다. 싱글톤만이 생성과 수명 관리의 변경을 줄이는 방법은 아니다.

반대로 사용자별 장바구니나 요청별 처리 상태처럼 호출자마다 다른 상태가 필요한 객체에는 맞지 않는다. 공유 객체에 상태를 넣는 순간, 한 요청의 변경이 다른 요청에 보이는지와 동시 접근을 함께 설계해야 한다.

## 장점과 한계

장점은 생성 비용을 줄이고 공유 대상을 한 곳에서 관리할 수 있다는 점이다. 같은 설정이나 자원 관리자에 접근하는 코드가 하나의 인스턴스를 사용하므로, 객체를 무분별하게 여러 개 만들지 않게 된다.

한계는 의존성이 숨기기 쉬워진다는 점이다. 어떤 클래스가 정적 접근 메서드를 직접 부르면 생성자만 봐서는 필요한 협력 객체를 알기 어렵고, 싱글톤의 상태나 동작을 바꾸면 이를 공유하는 모듈이 함께 영향을 받는다. 변경 전에 **이 싱글톤의 상태·설정을 바꾸면 어떤 모듈과 테스트가 영향을 받는가**를 확인해야 한다.

테스트도 조심해야 한다. 공유 인스턴스가 상태를 가진다면 한 테스트가 남긴 값이 다음 테스트에 남아 실행 순서에 따라 결과가 달라질 수 있다. 의존성을 생성자로 주입하고 테스트마다 대체 구현을 넘기는 구조가 필요할 때는, 싱글톤 직접 접근보다 그 경계를 분리하는 편이 낫다.

## Spring의 singleton scope와 같은가

이 절은 Spring을 사용할 때 읽으면 된다. Spring이 생성하고 관리하는 객체를 빈(bean)이라고 하고, 그런 객체들을 조립하고 관리하는 주체를 컨테이너라고 한다.

같은 용어를 쓰지만 보장 범위가 다르다. Java로 구현한 GoF 싱글톤은 보통 특정 클래스가 클래스 로더마다 하나의 인스턴스를 만들도록 클래스 수준에서 통제한다. 반면 Spring의 singleton scope는 하나의 Spring IoC 컨테이너에서 같은 bean 정의마다 하나의 공유 객체를 관리하는 기본 scope다.

따라서 같은 클래스로 bean을 둘 이상 등록하거나 컨테이너가 둘 이상이면 Spring에서는 인스턴스도 여럿일 수 있다. Spring bean에 `singleton`을 붙였다고 GoF 싱글톤 구현이 된 것은 아니며, 객체의 생성과 범위를 컨테이너에 맡긴 결과다.

## 기술면접 질문

### 싱글톤의 장점과 단점은 무엇인가

싱글톤은 생성 비용이 큰 객체를 한 번 만들고 공유하여 불필요한 생성 비용을 줄일 수 있습니다. 반면 전역 접근점이 되기 쉬워 모듈 간 의존성이 커지고, 공유 상태를 변경하면 사용 중인 여러 모듈에 영향이 퍼질 수 있습니다. 예를 들어 사용자별 장바구니처럼 호출자마다 다른 상태를 싱글톤으로 공유하면 한 사용자의 변경이 다른 사용자에게 노출될 수 있습니다.

### 싱글톤이 테스트를 어렵게 하는 이유는 무엇인가

싱글톤은 같은 인스턴스를 여러 테스트가 공유하게 만들어 테스트 사이의 상태 격리를 어렵게 합니다. 한 테스트가 설정이나 내부 상태를 바꾸면 다음 테스트가 그 값을 볼 수 있어 실행 순서에 따라 결과가 달라질 수 있습니다. 예를 들어 테스트 대역으로 교체할 경계가 없는 정적 싱글톤은 매 테스트마다 공유 상태를 초기화해야 하는 추가 비용을 만듭니다.

### Spring singleton bean은 싱글톤 패턴과 동일한 개념인가

동일하지 않습니다. GoF 싱글톤은 클래스 로더마다 특정 클래스의 인스턴스 하나를 보장하지만, Spring singleton bean은 컨테이너와 bean 이름 범위에서 하나의 객체를 관리합니다. 따라서 같은 클래스를 여러 bean으로 등록하거나 컨테이너가 여러 개이면 Spring에서는 인스턴스가 여러 개 생길 수 있습니다.

## 복습 체크리스트

- [ ] `private` 생성자와 정적 인스턴스·접근 메서드가 각각 필요한 이유를 설명할 수 있다.
