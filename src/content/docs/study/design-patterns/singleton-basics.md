## 핵심 요약

싱글톤 패턴은 특정 클래스의 인스턴스를 하나만 만들고, 여러 호출자가 그 인스턴스를 공유하게 하는 생성 패턴이다. 생성 비용이 큰 자원을 매번 만들지 않아도 된다는 이점이 있지만, 공유 상태와 전역 접근은 의존성과 테스트 비용을 키울 수 있다.

따라서 "하나면 충분한가"보다 **이 객체의 생성·공유·변경이 다른 모듈에 어떤 영향을 주는가**를 먼저 확인해야 한다. 다음 글에서는 이 기본 구조가 동시 호출에서도 하나만 생성되도록 만드는 구현 방식을 비교한다.

## 싱글톤이 해결하려는 문제

데이터베이스 연결처럼 생성과 해제에 I/O 비용이 드는 자원을 요청마다 새로 만들면, 실제 업무보다 연결 과정에 시간을 쓰게 될 수 있다. 여러 모듈이 같은 자원을 사용해도 괜찮다면 한 번 만든 객체를 공유하여 그 반복 비용을 줄일 수 있다.

다만 데이터베이스 연결을 클래스 하나의 인스턴스로만 관리해야 한다는 뜻은 아니다. 실제 서비스에서는 보통 여러 연결을 재사용하는 커넥션 풀을 사용하며, 풀 자체를 어떻게 생성·공유할지와 개별 연결의 개수는 별도 문제다. 싱글톤은 공유가 필요한 객체의 수명과 접근점을 정하는 선택이지, 모든 비싼 자원을 하나로 제한하는 규칙이 아니다.

## 하나의 인스턴스를 보장하는 구조

구조는 단순하다. 생성자를 `private`으로 감춰 외부의 `new`를 막고, 클래스 내부가 가진 정적 인스턴스를 정적 접근 메서드로 돌려준다. 호출자는 항상 같은 접근점을 거치므로 같은 객체를 받는다.

이 예시는 개념을 보여 주는 가장 작은 형태다. 여러 스레드가 동시에 처음 접근할 때의 안전한 초기화 방식은 다음 글에서 다룬다.

## Java로 보는 최소 예시

```java
public final class AppSettings {
    private static final AppSettings INSTANCE = new AppSettings();

    private AppSettings() {
    }

    public static AppSettings getInstance() {
        return INSTANCE;
    }
}
```

`new AppSettings()`는 클래스 내부에서 한 번만 실행된다. 외부 코드는 `AppSettings.getInstance()`로만 인스턴스에 접근하므로, `AppSettings`를 사용하는 곳은 모두 같은 객체를 참조한다.

## 어디에 사용할 수 있는가

공유해도 안전하고, 생성 또는 초기화 비용을 줄일 근거가 있는 객체에 후보가 된다. 예를 들어 애플리케이션 전역 설정을 읽기 전용으로 제공하는 객체나, 하나의 커넥션 풀을 관리하는 객체를 검토할 수 있다.

예를 들어 설정 초기화 결과를 여러 곳에서 공유하고 캐시해야 한다고 가정해 보자. 싱글톤이 없다면 각 호출자나 객체 조합 지점에서 생성·수명 관리 코드를 바꿔야 하지만, 싱글톤을 쓰면 인스턴스 생성은 `AppSettings`에 모이고 호출부는 기존 접근점을 유지한다. 다만 의존성 주입도 정적 전역 접근 없이 객체의 수명을 한곳에서 관리할 수 있으므로, 싱글톤만이 이 변경을 줄이는 방법은 아니다.

반대로 사용자별 장바구니나 요청별 처리 상태처럼 호출자마다 다른 상태가 필요한 객체에는 맞지 않는다. 공유 객체에 상태를 넣는 순간, 한 요청의 변경이 다른 요청에 보이는지와 동시 접근을 함께 설계해야 한다.

## 장점과 한계

장점은 생성 비용을 줄이고 공유 대상을 한 곳에서 관리할 수 있다는 점이다. 같은 설정이나 자원 관리자에 접근하는 코드가 하나의 인스턴스를 사용하므로, 객체를 무분별하게 여러 개 만들지 않게 된다.

한계는 의존성이 숨기기 쉬워진다는 점이다. 어떤 클래스가 정적 접근 메서드를 직접 부르면 생성자만 봐서는 필요한 협력 객체를 알기 어렵고, 싱글톤의 상태나 동작을 바꾸면 이를 공유하는 모듈이 함께 영향을 받는다. 변경 전에 **이 싱글톤의 상태·설정을 바꾸면 어떤 모듈과 테스트가 영향을 받는가**를 확인해야 한다.

테스트도 조심해야 한다. 공유 인스턴스가 상태를 가진다면 한 테스트가 남긴 값이 다음 테스트에 남아 실행 순서에 따라 결과가 달라질 수 있다. 의존성을 생성자로 주입하고 테스트마다 대체 구현을 넘기는 구조가 필요할 때는, 싱글톤 직접 접근보다 그 경계를 분리하는 편이 낫다.

## Spring의 singleton scope와 같은가

같은 말이지만 범위가 다르다. GoF 싱글톤은 특정 클래스가 클래스 로더마다 하나의 인스턴스만 만들도록 클래스 수준에서 보장하는 패턴이다. 반면 Spring의 singleton scope는 하나의 Spring IoC 컨테이너에서 같은 bean 이름(정의)에 대해 하나의 공유 객체를 관리하는 기본 scope다.

따라서 같은 클래스로 bean을 둘 이상 등록하거나 컨테이너가 둘 이상이면 Spring에서는 인스턴스도 여럿일 수 있다. Spring bean에 `singleton`을 붙였다고 GoF 싱글톤 구현이 된 것은 아니며, 객체의 생성과 범위를 컨테이너에 맡긴 결과다.

## 기술면접 질문

### 싱글톤의 장점과 단점은 무엇인가

싱글톤은 생성 비용이 큰 객체를 한 번 만들고 공유하여 불필요한 생성 비용을 줄일 수 있습니다. 반면 전역 접근점이 되기 쉬워 모듈 간 의존성이 커지고, 공유 상태를 변경하면 사용 중인 여러 모듈에 영향이 퍼질 수 있습니다. 그래서 공유가 안전한지와 변경 영향 범위가 비용 절감 이점보다 작은지를 보고 적용합니다.

### 싱글톤이 테스트를 어렵게 하는 이유는 무엇인가

싱글톤은 같은 인스턴스를 여러 테스트가 공유하게 만들어 테스트 사이의 상태 격리를 어렵게 합니다. 한 테스트가 설정이나 내부 상태를 바꾸면 다음 테스트가 그 값을 볼 수 있어 실행 순서에 따라 결과가 달라질 수 있습니다. 의존성을 주입하고 테스트용 구현으로 바꿀 수 있게 설계하면 이 결합을 줄일 수 있습니다.

### Spring singleton bean은 싱글톤 패턴과 동일한 개념인가

동일하지 않습니다. GoF 싱글톤은 클래스 로더마다 특정 클래스의 인스턴스 하나를 보장하지만, Spring singleton bean은 컨테이너와 bean 이름 범위에서 하나의 객체를 관리합니다. 따라서 같은 클래스를 여러 bean으로 등록하거나 컨테이너가 여러 개이면 Spring에서는 인스턴스가 여러 개 생길 수 있습니다.

## 복습 체크리스트

- [ ] `private` 생성자와 정적 인스턴스·접근 메서드가 각각 필요한 이유를 설명할 수 있다.
- [ ] 공유 상태의 변경이 어떤 모듈과 테스트에 영향을 주는지 점검할 수 있다.
