## 핵심 요약

대역폭은 링크가 이론적으로 수용할 수 있는 최대 전송 용량이고, 실제로 성공한 전송의 관측값인 처리량과는 다르다. 트래픽이 늘면 처리량이 함께 늘 수 있지만, 혼잡·재전송·서버와 장비의 자원 제약 때문에 처리량이 대역폭만큼 나오지는 않는다. API가 느릴 때는 네트워크 왕복 시간인 RTT와 애플리케이션 처리 시간을 분리해 살펴야 원인을 한쪽으로 단정하지 않을 수 있다.

| 용어 | 뜻 | 혼동을 막는 확인 질문 |
| --- | --- | --- |
| 트래픽 | 일정 시간 동안 링크를 오간 데이터의 양 또는 흐름이다. | 같은 시간대에 요청 수나 전송 데이터가 갑자기 늘었는가? |
| 처리량 | 링크에서 성공적으로 전달된 데이터의 양을 시간 기준으로 관찰한 값이다. | 실제로 전달 완료된 데이터가 얼마나 되는가? |
| 대역폭 | 연결이 단위 시간에 보낼 수 있는 최대 비트 수, 즉 용량의 상한이다. | 링크의 최대 용량은 얼마이며 실제 처리량과 차이가 나는가? |
| RTT | 요청 신호를 보내고 응답 또는 확인을 받기까지의 왕복 시간이다. | 호출 대상까지 왕복하는 네트워크 지연이 증가했는가? |

## 트래픽과 처리량의 차이

트래픽은 링크 위로 흐르려는 데이터의 양을 말하므로, 요청이 몰리거나 큰 응답을 전송할 때 증가한다. 처리량은 그중 실제로 성공해 전달된 데이터의 양을 나타내므로, 같은 트래픽이라도 오류·손실·재전송이 많으면 낮아질 수 있다. 즉 트래픽은 부하의 규모를, 처리량은 전달 결과를 이해하기 위한 지표다.

예를 들어 REST API의 목록 응답 크기가 커지고 호출 수가 늘면 서비스와 네트워크에 흐르는 트래픽은 증가한다. 그러나 연결이 혼잡하거나 서버가 응답을 제때 만들지 못하면 클라이언트가 체감하는 성공 전송량은 기대보다 낮을 수 있다. Kafka에서도 생산량이 늘었다는 사실과 소비자가 실제로 처리 완료한 레코드 수는 같은 지표가 아니므로 각각 관측해야 한다.

## 대역폭과 실제 처리량이 다른 이유

대역폭은 고속도로의 차선 수처럼 최대 용량을 설명하지만, 실제 처리량은 도로 위 차량 흐름처럼 여러 조건의 영향을 받는다. 동시 사용자 증가, 패킷 손실과 재전송, 프로토콜 오버헤드, 중간 장비의 제약, 송수신 애플리케이션의 처리 능력은 실제 처리량을 낮출 수 있다. 따라서 넓은 대역폭을 확보했다는 사실만으로 API가 그만큼 빠르거나 많은 데이터를 처리한다고 결론 내릴 수 없다.

gRPC 스트리밍은 메시지를 연속 전송해 왕복 횟수를 줄일 수 있지만, 수신 서비스의 역압력이나 중간 경로의 혼잡이 있으면 기대 처리량이 나오지 않을 수 있다. 외부 API 호출도 우리 서비스의 링크 대역폭만이 아니라 상대 서비스의 응답 생성, 경로, 제한 정책의 영향을 함께 받는다. 성능을 판단할 때는 대역폭 설정값과 관측 처리량을 나란히 보고, 차이가 난 구간을 추가로 확인한다.

## RTT가 API 응답 시간에 미치는 영향

RTT는 클라이언트와 서버 또는 두 서비스 사이에서 요청과 응답이 왕복하는 데 걸리는 네트워크 시간이다. REST API나 gRPC의 동기 호출은 왕복이 필요한 만큼 RTT가 커지면 네트워크 구간만으로도 응답 대기 시간이 늘어난다. 다만 전체 API 응답 시간에는 요청 전송, 응답 전송, 서버의 애플리케이션 처리, 데이터 저장소와 외부 의존성 대기가 함께 포함된다.

원인을 판단할 때는 **애플리케이션 처리 시간과 네트워크 왕복 시간을 분리**해서 기록하고 비교한다. 서버 내부 처리나 PostgreSQL 쿼리 대기가 길다면 RTT가 안정적이어도 API는 느릴 수 있고, 외부 API까지의 RTT가 증가하면 애플리케이션 처리가 빨라도 호출 전체가 늦어질 수 있다. Kafka처럼 비동기로 전달하는 흐름에서는 사용자 요청의 즉시 응답 시간과 소비 완료까지의 지연을 별도로 측정해 동기 API의 RTT와 혼동하지 않는다.

API 응답 시간이 증가하면 다음 순서로 확인한다.

1. 요청과 응답의 데이터 크기가 변했는지 확인해 전송해야 할 양 자체가 커졌는지 본다.
2. 링크의 대역폭과 실제 처리량을 비교해 혼잡, 재전송, 중간 장비 또는 송수신 측 제약이 있는지 살핀다.
3. 서비스 간 또는 외부 API까지의 RTT를 비교해 네트워크 왕복 시간이 늘었는지 확인한다.
4. 컨트롤러 이후의 애플리케이션 처리 시간, 데이터베이스·외부 의존성 대기 시간을 따로 확인해 네트워크 지연과 구분한다.

## 장점과 한계

트래픽·처리량·대역폭·RTT를 구분하면 관측값을 하나로 뭉뚱그리지 않고, 병목을 찾기 위한 질문을 순서대로 세울 수 있다. 특히 네트워크 왕복 시간과 서버 처리 시간을 나누면 네트워크 증설, 쿼리 개선, 호출 방식 변경 중 어느 방향을 먼저 검토할지 근거를 만들 수 있다.

그러나 이 지표들만으로 API 지연의 원인을 확정할 수는 없다. 측정 지점과 시간 구간이 다르면 값의 의미가 달라지고, 캐시·큐 적체·상대 서비스의 제한 같은 요인은 별도 관측이 필요하다. 그래서 지표는 결론이 아니라 다음 조사 범위를 좁히는 신호로 사용해야 한다.

## 기술면접 질문

### 대역폭과 처리량의 차이

대역폭은 연결이 단위 시간에 전송할 수 있는 최대 용량이고, 처리량은 실제로 성공해 전달된 데이터의 관측값입니다. 혼잡, 재전송, 장비 성능, 송수신 애플리케이션의 처리 능력 때문에 처리량은 대역폭보다 낮을 수 있습니다. 따라서 대역폭이 높다는 사실만으로 서비스가 그만큼 빠르다고 판단할 수 없습니다.

### RTT가 API 응답 시간에 주는 영향

RTT는 요청을 보낸 뒤 응답 또는 확인을 받을 때까지의 네트워크 왕복 시간입니다. 동기 REST API나 gRPC 호출에서는 RTT가 증가하면 애플리케이션 처리와 별개로 대기 시간이 늘어납니다. 전체 응답 시간은 RTT뿐 아니라 전송 시간과 서버·데이터베이스·외부 의존성 처리 시간도 포함하므로 함께 측정해야 합니다.

### 네트워크 병목과 애플리케이션 지연을 구분하는 방법

먼저 데이터 크기와 대역폭 대비 실제 처리량을 확인해 전송량 또는 링크 혼잡의 신호가 있는지 봅니다. 다음으로 서비스 간 RTT와 애플리케이션 처리 시간을 분리해 같은 시간대의 변화를 비교합니다. RTT가 안정적인데 처리 시간이 길면 서버 내부나 의존성 대기를 우선 조사하고, RTT가 함께 증가하면 네트워크 경로나 호출 대상도 조사합니다.
