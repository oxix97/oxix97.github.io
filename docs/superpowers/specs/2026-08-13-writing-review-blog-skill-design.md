# 복습형 기술 블로그 작성 스킬 설계

## 목적

`oxix97's Dev Log`의 신규 기술 글 작성과 기존 글 수정을 일관되게 지원하는 개인 Codex 스킬을 만든다. 기존 글의 정확성, 출처, 시리즈 구조는 유지하면서 글쓴이의 학습 계기와 실제로 헷갈렸던 지점이 드러나는 자연스러운 복습형 문체를 적용한다.

## 설치 위치와 구성

스킬은 저장소의 `.agents/skills/writing-review-blog/`에 둔다.

```text
.agents/skills/writing-review-blog/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── references/
    ├── style-guide.md
    └── article-template.md
```

- `SKILL.md`: 발동 조건, 신규 작성·기존 글 수정 워크플로, 검증 계약을 정의한다.
- `references/style-guide.md`: 문체, 구조, 보존 대상, 금지 사항과 최종 체크리스트를 보관한다.
- `references/article-template.md`: 이 저장소의 frontmatter와 복습형 기술 글 본문 구조를 제공한다.
- `agents/openai.yaml`: Codex UI에서 사용할 표시 이름, 설명, 기본 프롬프트를 제공한다.

별도 스크립트는 만들지 않는다. 문장 길이와 개인 경험의 진위처럼 기계적 검사만으로 판단하기 어려운 항목이 핵심이기 때문이다.

## 발동 범위

다음 요청에 스킬이 발동하도록 description을 작성한다.

- oxix97 Dev Log의 기술 글 초안 작성
- 기존 study 글의 자연스러운 문체 수정
- 기술 개념 복습 글, 면접 대비 글, 시리즈 글 작성
- 블로그 글의 구조·문체·출처·복습 체크리스트 점검

일반적인 블로그 글이나 다른 저장소의 문서 작업에는 자동으로 적용하지 않는다.

## 작성 워크플로

1. 신규 작성인지 기존 글 수정인지 구분한다.
2. 대상 글과 같은 시리즈의 인접 글을 읽어 frontmatter, 링크, 용어, 다이어그램 패턴을 파악한다.
3. 사용자가 제공한 자료와 실제 학습 메모를 확인한다.
4. 실제로 헷갈렸던 지점이 제공되지 않았다면 이를 창작하지 않고 사용자에게 한 가지 질문으로 요청한다.
5. 정확성 확인이 필요하면 RFC, 표준, 공식 문서, 공식 프로젝트 문서를 우선 조사한다.
6. 정해진 글 구조와 문체 계약에 따라 초안을 작성하거나 원문을 수정한다.
7. 기술 정확성, 출처, 링크, frontmatter, 문체, 시리즈 연결을 최종 점검한다.

## 출력 계약

### 문체

- 본문은 감정 과잉이 없는 편한 `-다`체로 쓴다.
- 기술면접 답변은 기존 글과 일관되게 `-습니다`체를 유지한다.
- 긴 문장은 가능하면 15~20단어를 기준으로 나누되, 의미가 끊기거나 부자연스러워지면 문맥을 우선한다.
- 정의를 곧바로 제시하기보다 짧은 복습 계기에서 시작한다.
- 표와 다이어그램 앞뒤에는 자연스러운 연결 문장을 둔다.

### 구조

다음 흐름을 기본 계약으로 유지한다.

```text
복습 계기 → 핵심 요약 → 개념·문제 설명 → 구조·원리
→ 코드·표·다이어그램 → 장점과 한계 → 기술면접 질문
→ 복습 체크리스트 → 참고 자료 → 이전·다음 글 연결
```

주제 특성상 코드나 표가 필요하지 않으면 해당 요소는 생략할 수 있지만, 기술면접 질문·복습 체크리스트·참고 자료는 유지한다.

### 보존 항목

- frontmatter의 기존 필드와 저장소 형식
- 검증된 RFC 및 공식 문서 출처
- 기존 SVG 경로, 대체 텍스트, 캡션
- 섹션별 핵심 판단 기준을 나타내는 굵은 문장
- 시리즈의 이전·다음·목록 링크

### 금지 항목

- 사용자가 제공하지 않은 개인 경험, 감정, 시행착오 창작
- 검증하지 않은 기술적 단정
- 출처를 확인하지 않은 링크 또는 존재하지 않는 참고 자료
- 정확성을 희생한 과도한 구어체
- 기존 다이어그램이나 시리즈 링크의 불필요한 교체

## 오류와 불확실성 처리

- 개인 학습 경험이 빠졌으면 가상의 경험을 넣지 않고 질문한다.
- 근거가 충돌하면 공식·1차 출처를 우선하며, 구현별 차이가 있으면 범위를 명시한다.
- 기존 글의 기술 오류를 발견하면 문체 수정과 구분해 사용자에게 알리고 근거와 함께 수정한다.
- 링크 또는 시리즈 순서를 저장소에서 확인할 수 없으면 추측하지 않고 확인이 필요하다고 표시한다.

## 검증 전략

스킬 작성 전후에 동일한 대표 요청을 비교한다.

1. 기존 TCP 글의 도입부와 한 섹션을 복습형 문체로 수정하는 요청
2. 사용자 학습 메모가 없는 상태에서 새 기술 글을 써 달라는 요청
3. SVG, 참고 자료, 기술면접 질문을 가진 기존 글 전체를 다듬는 요청

성공 기준은 다음과 같다.

- 개인 경험을 지어내지 않고 필요한 입력을 요청한다.
- 기존 구조, frontmatter, 다이어그램, 출처를 보존한다.
- 본문은 편한 `-다`체, 면접 답변은 `-습니다`체를 사용한다.
- 핵심 판단 문장과 복습 체크리스트를 유지한다.
- 신규 글과 기존 글 수정 양쪽에서 동일한 품질 계약을 적용한다.

완성 후 `quick_validate.py`로 스킬 구조를 검사하고, 대표 요청으로 전방 테스트한다.
